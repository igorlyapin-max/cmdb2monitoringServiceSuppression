# Инструкция редактора правил и моделей

Эта инструкция описывает рабочий процесс оператора, который готовит CMDBuild
модель мониторинга, настраивает правила конвертации и управляет шаблонами
автонаполнения через Monitoring UI.

## Роль редактора

Редактор управляет конфигурацией, а не исполняет runtime-логику вручную.
Monitoring UI готовит схемы, правила, шаблоны и управляемые связи. Микросервисы
читают уже опубликованные правила, принимают webhooks из CMDBuild, пишут
события в Kafka и применяют рассчитанные изменения в Zabbix и CMDBuild.

Основные границы:

- `monitoring-ui-api` является точкой редактирования правил, шаблонов и схемы.
- `cmdbconfigbuilder` исполняет обычные правила конвертации, включая правила,
  созданные из шаблонов.
- `zabbixconfig2api` применяет Zabbix-сторону.
- `cmdbaggregation2cmdbuild` применяет CMDBuild-сторону, включая managed
  объекты и связи.
- Шаблоны не исполняются напрямую микросервисами. UI материализует их в обычные
  правила с `generated_from_template`.

## Перед началом работы

Проверьте условия развертывания:

1. Инфраструктура из [DEPLOYMENT.md](DEPLOYMENT.md) развернута: CMDBuild,
   Zabbix, Kafka, опционально PAM/AAPM.
2. Kafka topics созданы заранее. Сервисы не создают topics при старте.
3. Все сервисы отвечают на `/health`, а Monitoring UI показывает их в
   верхней панели.
4. В `zabbixconfig2api`, `cmdbaggregation2cmdbuild` и `monitoring-ui-api`
   настроен один и тот же Bearer token для перезагрузки конфигурации.
5. Папка `conversionConfig.storageFolder` подключена как постоянное серверное
   хранилище. Ее пишет только `monitoring-ui-api`.
6. В CMDBuild есть или будет создан атрибут готовности source-карточек к
   Zabbix, по умолчанию `zabbix_main_hostid`.

Перед редактированием в UI выполните синхронизацию источников:

1. `Синхронизация с источниками данных -> CMDBuild`: загрузить классы,
   атрибуты, domains и текущие managed-карточки.
2. `Синхронизация с источниками данных -> Zabbix`: проверить доступность API.
3. `Синхронизация с источниками данных -> Webhooks`: проверить endpoint и
   managed webhooks.
4. `Синхронизация с источниками данных -> Конфигурации конвертации`: загрузить
   текущие правила, шаблоны и управляемые связи из серверной папки.

## Управление схемой CMDBuild

Откройте `Управление схемами` отдельно для сервисного слоя и слоя подавления.
Выберите язык, prefix и root модели. Пустой root нормализуется по языку:
`/Мониторинг` для `ru`, `/Monitoring` для `en`.

Схема строится под managed superclass:

- сервисный слой: `C2M_ServiceManagedObject`;
- слой подавления: `C2M_SuppressionManagedObject`.

Planned объекты показывают то, что builder рекомендует создать. Ready объекты
уже существуют под выбранным root и наследуются от правильного managed
superclass. Если класс с тем же code существует в другой ветке, это конфликт
CMDBuild-модели. Такой класс нужно перенести или пересоздать вручную, потому
что apply не должен молча менять parent.

При отправке выбранных объектов в CMDBuild:

- planned rows выбраны по умолчанию;
- ready rows можно выбрать вручную для идемпотентного обновления;
- lookup-зависимости добавляются автоматически;
- existing classes/domains пропускаются;
- результат create/skip/fail возвращается в UI.

Сервисный класс `ServiceUserEndpointFleet` нужен для управляемых групп рабочих
мест, например "все ноутбуки", "тонкие клиенты офиса", "АРМ call-center".
Внутрь должны попадать агрегирующие managed-карточки пользовательских endpoint,
а не серверы, базы данных, сетевое оборудование или платформенные сервисы.

## Статические правила

Откройте слой `Сервис -> Статические правила` или
`Подавление -> Статические правила`.

Порядок настройки:

1. Выберите действие с правилом: создать, изменить или удалить.
2. Выберите `Класс-источник`. Это customer CMDBuild class, откуда приходят
   карточки и webhooks.
3. Выберите `Целевой класс\экземпляр класса`.
4. Если выбран класс, UI создаст или обеспечит target-карточку и покажет
   разрешенные атрибуты target-объекта. Если выбран существующий экземпляр,
   правило будет привязано к нему без создания новой карточки.
5. Настройте `Условия выборки объектов`.
6. Сохраните правило, проверьте preview, затем примените конфигурацию.

В target-атрибутах создаваемого объекта можно использовать только данные
выбранного source-класса:

- `${class.code}`;
- `${class.description}`;
- `${class.hierarchyPath}`;
- `extract(...)`, `replace(...)`, `lower(...)`, `upper(...)`, `trim(...)`,
  `default(...)` над этими значениями.

`${source.*}` нельзя использовать в атрибутах создаваемого target-объекта,
потому что конкретная source-карточка еще не обрабатывается. `${source.*}`
используется в runtime-маппингах обычного правила, когда уже пришло событие по
конкретной карточке.

## Условия выборки объектов

Условия выборки являются boolean-фильтрами карточек:

- все строки `Включить` работают совместно как AND;
- любая строка `Исключить` удаляет карточку из результата;
- regex-группы в условиях не создают переменные автоматически;
- для вырезки значений используйте `extract` в шаблоне или target-поле, когда
  значение известно при применении шаблона.

Примеры:

- `(?i)^active$`: статус равен active без учета регистра;
- `^prod-.*`: значение начинается с `prod-`;
- `.*\\.corp\\.example$`: DNS заканчивается на `.corp.example`;
- `^$`: пустое значение;
- `.+`: непустое значение;
- exclude `^test-.*`: убрать тестовые объекты.

## Шаблоны автонаполнения

Шаблон нужен, когда одинаковое правило должно быть создано для многих
source-классов. Например, один шаблон может создать правила для классов
`NTBook`, `ThinClient` и `ARM`, если они должны попадать в одинаковую
управляемую группу.

Поля шаблона:

- `Source class regex`: выбирает candidate source-классы по code,
  description/display name или hierarchy path;
- `Target class`: managed class, куда будут привязаны generated-правила;
- `Атрибуты source для копирования`: тот же список source-полей, что и в
  условиях выборки; из него можно скопировать идентификатор поля для regex
  conditions или выражение `${source.<identifier>}` для runtime-шаблонов;
- `Измерение population`: набор значений, по которым шаблон развернется в
  статические правила;
- `name`, `initial description`: шаблонные выражения для generated-правил и
  target-объектов; в materialized-шаблонах они могут читать `template.*`,
  `class.*`, `dimension.*` и `vars.*`, но не `${source.*}`;
- `Атрибуты создаваемого target-объекта`: пользовательские поля агрегата,
  которые будут записаны при создании target-card. В service-шаблонах UI
  и suppression-шаблонах UI показывает `is_critical`, `aggregation_type`,
  `threshold`, `n`, если они есть в выбранном классе. Эти значения могут читать
  `template.*`, `class.*`, `dimension.*` и `vars.*`, но не `${source.*}`;
- `population_source_key`: служебный ключ managed target. В materialized
  шаблонах он формируется из ключа измерения, обычно
  `${template.id}:${dimension.key}`, и в UI не редактируется напрямую;
- `Variables`: промежуточные значения, которые можно использовать как
  `${vars.name}`;
- `Условия выборки объектов`: фильтры карточек, которые попадут в каждое
  generated-правило.

### Измерение population

Шаблон больше не должен создавать target-объект с динамическими атрибутами вида
`${source.*}`. Конкретная source-карточка еще не обрабатывается в момент
материализации, поэтому target `name`, `description` и `idempotency_key` должны
быть статическими для конкретного generated-правила.

UI материализует шаблон по схеме:

```text
candidate source class x dimension value -> generated conversion rule
```

Например, `Source class regex = (?i).*(Ноутбук|Тонкий клиент|АРМ).*` и
измерение "город" создают отдельные правила для каждой пары
`NTBook/город`, `ThinClient/город`, `ARM/город`. Если `Шаблон ключа` равен
`${template.id}:${dimension.key}`, все source-классы одного шаблона будут
обеспечивать один target-объект на город; если нужен отдельный target на класс,
используйте `${template.id}:${class.code}:${dimension.key}`.

Поддерживаемые типы измерений:

- `Distinct source field`: UI перед применением подгружает карточки
  candidate source class и берет уникальные значения выбранного поля.
- `Lookup values`: берет значения lookup из CMDBuild metadata; если lookup не
  найден, может использовать значения карточек.
- `Bool values`: заранее создает два значения `true` и `false`.
- `Reference/domain values`: использует выбранный развернутый path как поле
  условия; resolved paths при этом классифицируются по конечному leaf-типу, а
  не по факту наличия reference/domain в пути.
- `Regex capture from source field`: читает source-поле, применяет regex и
  берет capture group как `dimension.key`.
- `Range/list generator`: создает значения из диапазона, например `00-99`.
- `Static list`: принимает строки `key|name|condition-regex`. Третья часть
  необязательна; если она задана, она становится regex условия для правила.
- `Legacy: one rule per class`: совместимый режим старых шаблонов.

Reference/domain path считается пригодным только когда UI дошел до конечного
leaf-атрибута. Если leaf является lookup, поле показывается в `Lookup values`;
если boolean, в `Bool values`; строковые и числовые leaf-атрибуты попадают в
distinct/regex. Если рекурсии не хватило и обход остановился на ссылке на
объект, поле помечается как неразрешенная object reference. Такой вариант
показывается только диагностически и шаблон с ним сохранить нельзя: увеличьте
глубину рекурсии или выберите конечный leaf.

### Какие поля измерения population заполняет пользователь

Заполняйте блок сверху вниз. Сначала выберите `Source class regex` и
синхронизируйте каталог CMDBuild, затем выберите `Тип развертки`. После этого UI
показывает только те поля, которые участвуют в выбранном типе. Скрытые поля не
попадают в сохраненный шаблон.

Словарь `dimension.*`:

| Токен | Что означает | Откуда берется | Где использовать |
| --- | --- | --- | --- |
| `${dimension.key}` | Стабильный ключ значения измерения | Для distinct/regex/range обычно само значение; для lookup это lookup code; для bool `true` или `false`; для static list левая часть строки `key|name|condition-regex`; для regex capture выбранная capture group | В `Шаблон ключа`, managed/idempotency key, и в местах, где нужен стабильный технический идентификатор |
| `${dimension.value}` | Значение измерения как строка для сравнения | Обычно совпадает с `${dimension.key}`; UI использует его для точного regex-условия, если `Regex отбора source-карточек` пустой | В простых именах и условиях, когда отображение и ключ одинаковые, например `Город ${dimension.value}` |
| `${dimension.name}` | Отображаемое имя значения измерения | Результат поля `Шаблон имени ${dimension.name}`; внутри самого этого поля `${dimension.name}` означает исходное display name до шаблона | В target `Шаблон name`, когда нужен человекочитаемый текст |
| `${dimension.regexKey}` | Regex-safe версия `${dimension.key}` | UI экранирует спецсимволы regex | В `Regex отбора source-карточек`, например `(?i)^w${dimension.regexKey}[0-9]{2}-.*$` |

Иными словами, `key` нужен для стабильной идентификации, `value` для значения,
по которому можно сравнивать карточки, `name` для текста в создаваемом объекте,
а `regexKey` для безопасной вставки ключа внутрь регулярного выражения.

В раскрытой подсказке `Что такое dimension.*` редактор показывает текущий
предпросмотр. После выбора типа и заполнения полей UI выводит первые рассчитанные
`dimension.key`, `dimension.value`, `dimension.name`, `dimension.regexKey` и
итоговый target key по `Шаблон ключа target`. Для `Distinct source field` и
`Regex capture` предпросмотр использует уже загруженные карточки source-класса;
если карточки не синхронизированы, preview покажет, что значений пока нет.
Если выбран reference path вроде `locationFloorBuildingCity`, применение
шаблона догружает промежуточные классы path и берет значение конечного leaf
атрибута, например `ARM.Location.Floor.Building.City -> Building.City`.
Сам preview тоже пытается догрузить необходимые source/reference карточки и
перерисоваться после загрузки.

| Поле | Когда видно | Нужно ли редактировать | Что вносить |
| --- | --- | --- | --- |
| `Тип развертки` | всегда | да, это первое решение | Источник множества значений измерения: distinct field, lookup, bool, regex capture, range/list, static list или legacy. |
| `Атрибут/path source` | `Distinct source field`, `Lookup values`, `Bool values`, `Regex capture`, диагностические unresolved links | да | Конечный leaf-атрибут карточки source или развернутый reference/domain path. Для lookup/bool UI показывает поля по leaf-типу. Для `locationFloorBuildingCity` значениями измерения станут найденные города. |
| `Regex вырезки значения` | `Regex capture from source field` | да | Regex, который вырезает ключ из значения выбранного source-поля, например `(?i)^w([0-9]{2})[0-9]{2}-.*$`. |
| `Группа -> ${dimension.key}` | `Regex capture from source field` | обычно `1` | Номер или имя capture group. Значение выбранной группы становится `${dimension.key}`. Если regex `(?<city>[0-9]{2})`, можно указать `city`; если обычные скобки, чаще `1`. |
| `Значения измерения / диапазон` | `Range/list generator`, `Static list` | да | Для диапазона: `00-99`. Для списка: строки `key|name|condition-regex`; `key` станет `${dimension.key}`, `name` станет базовым именем для `${dimension.name}`, третья часть необязательна. |
| `Шаблон ключа target` | все materialized-типы, кроме legacy | обычно оставить по умолчанию | Stable key target-объекта. `${template.id}:${dimension.key}` дает один target на значение измерения для всех source-классов шаблона. `${template.id}:${class.code}:${dimension.key}` создает отдельный target на пару класс/значение. |
| `Шаблон имени ${dimension.name}` | все materialized-типы, кроме legacy | обычно оставить по умолчанию | Формирует итоговое `${dimension.name}`. Внутри этого поля `${dimension.name}` означает базовое display name до шаблона. Частые варианты: `${dimension.value}`, `${dimension.name}`, `Город ${dimension.value}`, `${class.description}: ${dimension.name}`. |
| `Поле отбора source-карточек` | `Regex capture`, `Range/list generator`, `Static list` | да, если поле показано | Поле карточки, по которому generated-правило будет выбирать source-карточки. Для `Regex capture` обычно совпадает с `Атрибут/path source`; для range/static это обязательное поле. |
| `Regex отбора source-карточек` | `Regex capture`, `Range/list generator`, `Static list` | по ситуации | Regex условия generated-правила. Если пусто, UI строит точное совпадение со значением измерения. Для hostname-группировки: `(?i)^w${dimension.regexKey}[0-9]{2}-.*$`. |
| `Лимит правил` | все materialized-типы, кроме legacy | редко | Защита от случайного взрыва cardinality. Увеличивайте только если ожидаемое число generated-правил осознанно больше лимита. |

Поле `population_source_key` не предназначено для ручного редактирования. Это
служебный ключ managed target, который UI формирует из `Шаблон ключа`.

Тип `Неразрешенные reference/domain links` является диагностическим. Он
показывает paths, где обход остановился на ссылке на объект, а не дошел до
leaf-атрибута. Такой шаблон нельзя сохранить; увеличьте глубину рекурсии
domains/reference/lookups или выберите leaf-поле.

Пример для городов:

- если нужен один service/suppression target на город независимо от source-класса,
  оставьте `Шаблон ключа = ${template.id}:${dimension.key}`;
- если нужен отдельный target для `NTBook/City01`, `ThinClient/City01` и
  `ARM/City01`, используйте
  `Шаблон ключа = ${template.id}:${class.code}:${dimension.key}`;
- для имени можно указать `Город ${dimension.value}` или оставить
  `${dimension.value}`;
- при `Distinct source field` по `locationFloorBuildingCity` UI возьмет
  уникальные значения из карточек и добавит в каждое generated-правило условие
  отбора по этому path;
- при `Range/list generator` со значениями `01-99` обязательно заполните `Поле
  отбора source-карточек`, например `locationFloorBuildingCity`, а regex условия
  можно оставить пустым для точного совпадения или задать явно через
  `${dimension.regexKey}`.

Если `Source class regex` выбирает несколько классов, UI строит список
атрибутов для `Условия выборки объектов` так:

1. Находит candidate classes по regex. Проверяются code, display
   name/description и hierarchy path.
2. Для каждого candidate class берет активные читаемые атрибуты из
   синхронизированного CMDBuild schema catalog.
3. Reference-атрибуты разворачивает до листовых полей, например
   `Owner -> Email` становится идентификатором вроде `ownerEmail`.
4. Domain-связи разворачивает до domain leaf fields, например
   `domain NetworkSegment -> Code`.
5. Все варианты объединяет в один список.
6. Дубликаты схлопывает по нормализованному идентификатору поля.

Следствия:

- одинаковые inherited/common атрибуты показываются один раз, а не по одному
  разу на каждый класс;
- список является union, не intersection;
- если поле есть только у `NTBook`, но отсутствует у `ThinClient`, оно все
  равно может быть видно, потому что попало в общий union;
- один и тот же фильтр шаблона будет скопирован во все generated-правила;
- для общего шаблона выбирайте поля, которые реально есть у всех выбранных
  классов;
- если группы классов имеют разные наборы атрибутов, создайте несколько
  шаблонов с более узкими regex.
- поле, выбранное в измерении population, тоже должно быть доступно в payload
  webhooks для всех классов, где будет работать generated-правило.

UI не достраивает inherited attributes самостоятельно обходом parent-chain.
Унаследованные поля видны только если CMDBuild endpoint
`/classes/{class}/attributes` возвращает их для конкретного класса. Если
ожидаемого поля нет:

1. Выполните повторную синхронизацию CMDBuild.
2. Проверьте schema endpoint для конкретного класса.
3. Убедитесь, что атрибут active и имеет стабильный code.
4. При необходимости разделите template regex на несколько шаблонов.

Рекомендуемый формат `Source class regex`:

- `(?i)^(NTBook|Notebook|ThinClient|ARM)$`: точный выбор нескольких классов по
  "или";
- `(?i).*(Ноутбук|Тонкий клиент|АРМ).*`: поиск слов внутри code, description
  или path;
- `^/Monitoring/Workplaces/.*`: выбор ветки модели.

Не используйте `*` как файловую маску. В regex выражение
`(?!)*Тонкий клиент*` не означает "содержит Тонкий клиент". Для contains
используйте `(?i).*Тонкий клиент.*`.

## Применение шаблонов

Откройте `Управление правилами -> Создать/обновить правила по шаблонам и
связям` и выполните `Проверить шаблоны`. После успешной проверки без
блокирующих ошибок можно выполнить `Создать/обновить правила по шаблонам и
связям`.

Аудит строит план:

- считает enabled service/suppression templates;
- вычисляет candidate classes;
- рассчитывает значения `dimension.key`, `dimension.value`, `dimension.name`;
- генерирует обычные правила с `generated_from_template`;
- показывает create/update/unchanged/remove для правил и управляемых связей;
- показывает целевой класс, target key и пользовательские атрибуты цели
  (`aggregation_type`, `threshold`, `n`, `is_critical`, если они есть в
  целевом классе);
- выводит блокирующие ошибки по пустым dimension, незагруженным карточкам,
  отсутствующим target/domain и дублирующимся `rule_id`/managed key.

Эта операция не исполняет правила на текущих карточках CMDBuild. Она только
меняет конфигурацию правил и управляемых связей. Target-карточки service или
suppression создаются позже, когда `cmdbconfigbuilder` получит подходящий
webhook source-класса и `cmdbaggregation2cmdbuild` применит рассчитанную
команду. Если нужно построить объекты по уже существующим карточкам без
ручного изменения каждой карточки, используйте отдельную повторную обработку
source-классов/backfill; проверка и материализация шаблонов сами карточки не
переобрабатывают.

При сохранении шаблона UI увеличивает версию только при значимом изменении и
пишет immutable snapshot в `templateVersions`. При применении шаблонов UI не
пересоздает весь набор generated-правил. Он делает reconcile:

1. Строит desired-state для текущих версий шаблонов.
2. Сопоставляет generated artifacts по стабильному `managed_key`.
3. Сравнивает фактический payload через `artifact_fingerprint`.
4. Оставляет unchanged artifacts без перезаписи.
5. Обновляет только changed artifacts.
6. Создает missing artifacts.
7. Снимает obsolete artifacts и добавляет их target-объекты в
   `templateDeletionPlans`.

Ручные правила и detached generated rules сохраняются. Каждое применение
фиксируется в `templateApplications`: template id/version, content hash,
candidate source classes, generated managed keys и счетчики reconcile.

Удаление шаблона имеет два режима:

- отвязать generated-правила и сохранить созданные объекты;
- удалить generated-правила и добавить target-объекты в план ручной обработки.

Связи между шаблонами и связи template -> static CMDBuild class/card должны
формироваться по той же модели: stable `managed_key` не включает версию
шаблона, `artifact_fingerprint` отражает payload связи, а template version и
content hash хранятся только для трассировки и отката.

При применении шаблонов и связей UI разворачивает template-template связь в
обычные `relations` конкретных generated rules. Например связь шаблона
`Рабочие места` с шаблоном `Уровень коммутации` по переменной города создает в
правиле `Рабочие места / City14` runtime-связь на target lookup
`network-access-zone-by-city:City14`. CMDBuild applier создает физическую
relation только во время обработки source-события правила и только если обе
managed-карточки уже существуют. Если целевая карточка еще не создана,
переобработайте source-карточки после появления целевого объекта.
Для связи `шаблон -> шаблон` блоки отбора generated rules есть с обеих сторон:
отдельно для шаблона-источника и отдельно для целевого шаблона. Они работают
так же, как `Условия выборки объектов`: все строки `Включить` применяются
совместно как AND, строки `Исключить` вычитают совпавшие generated rules.
Фильтры не заменяют сопоставление пары. Они только ограничивают левый и правый
наборы кандидатов; после фильтрации UI все равно сравнивает выбранные
`source_variable` и `target_variable`, применяя `source_pattern` и
`target_pattern`, если они заданы. Например слева можно оставить только
`dimension_key / (?i)^City(04|14)$`, справа исключить
`dimension_key / (?i)^City00$`, а затем сопоставить `dimension_key =
dimension_key`.
Для связи `шаблон-правило` направление выбирается явно полями `Источник` и
`Назначение`. Оба списка содержат шаблоны и правила, но сохранить можно только
пару, где один конец является шаблоном, а второй правилом. `шаблон -> правило`
означает, что generated rules шаблона получат runtime-связи на конкретное
правило. `правило -> шаблон` означает, что конкретное правило получит
runtime-связи на matching generated rules выбранного шаблона, например правило
`Маршрутизаторы ядра` подавляет generated-зоны `City04` и `City14`.
Целевое правило может указывать на существующую CMDBuild-карточку; в таком
случае runtime-связь использует `target.card_id`, а не служебный
`idempotency_key`. Связи зависимости в service используют `relationType =
service_depends_on`; схема создает матрицу таких доменов между конкретными
управляемыми service-классами, включая custom-классы. Домены `member_of` и
`aggregates_to` остаются отдельной семантикой для состава/агрегации; self-link
generated rule с самим собой пропускается.
В слое подавления роль `Подавляет` можно использовать между любыми конкретными
suppression-классами. Схема создает матрицу доменов между такими классами:
если цель `SuppressionNetworkAccessZone`, используется `relationType =
depends_on_network`, для остальных целей `relationType = depends_on`. Поэтому
связи вроде `SuppressionComputeCluster -> SuppressionNetworkAccessZone` или
`SuppressionProxyGroup -> SuppressionStoragePool` не требуют ручного домена,
если актуальная схема уже применена в CMDBuild.
Если связать нужно не все generated-правила шаблона, заполните блок отбора на
той стороне, где выбран шаблон. Он работает так же, как `Условия выборки
объектов` в шаблоне: каждая строка `Включить` задает переменную шаблона и
regexp, все include-строки применяются совместно как AND; каждая строка
`Исключить` вычитает generated rule, если его переменная прошла regexp.
Например `Включить dimension_key / (?i)^City(04|14)$` оставит только правила
городов City04 и City14, а `Исключить dimension_key / (?i)^City00$` уберет
City00 из уже выбранного набора. Пустой блок отбора означает все generated
rules выбранного шаблона.
В редакторе `правило -> правило` галочка `Не показывать связи шаблонов`
включена по умолчанию. Она скрывает производные rule-rule связи с
`attributes.inherited_from_template_relation`, чтобы ручные связи не смешивались
со связями, которые были материализованы из шаблонов. Если нужно проверить
полный результат применения шаблонов, снимите галочку.

## Сохранение и публикация конфигурации

После изменения схемы, правил, шаблонов или управляемых связей:

1. В редакторе шаблона нажмите `Сохранить шаблон`. Это сохраняет шаблон в
   текущей UI-конфигурации, но еще не записывает серверную папку.
2. Если шаблон или связь должны изменить generated rules, откройте
   `Создать/обновить правила по шаблонам и связям` и выполните reconcile.
3. Проверьте preview, проверку шаблонов и разделы `Управление связями`.
4. Откройте `Синхронизация с источниками данных -> Конфигурации конвертации`.
5. Нажмите `Сохранить в папку`: UI сохранит правила, шаблоны и
   `managed_relations`, созданные при применении шаблонов и связей.
6. Если UI вернул conflict по manifest version/etag, загрузите папку заново,
   проверьте изменения и повторите сохранение.
7. Перезагрузите appliers через UI. Для этого используется общий Bearer token.
   Отдельной публикации правил в микросервисы нет: сохраненная общая папка
   является источником конфигурации для перечитывания. В целевой схеме этот же
   процесс будет читать Git-backed конфигурацию.
8. Проверьте, что health cards показывают новую running configuration version.
9. Выполните `Webhooks -> Опубликовать webhooks в CMDBuild`, если в правилах
   появились новые source-классы, затем `Webhooks -> Сверить правила онлайн`.
10. Для проверки runtime-результата измените подходящие source-карточки или
    нажмите `Верификация и применение -> Запросить применение текущих
    карточек`. Одного применения шаблонов недостаточно для появления новых
    target-карточек в CMDBuild.

Проверка webhooks группирует правила по source-классам. Она не создает и не
требует отдельный webhook на каждый generated `rule_id`: один и тот же
customer-класс, попавший в service и suppression правила, должен иметь
managed webhooks для `CREATE`, `UPDATE` и `DELETE` один раз на класс.
Публикация конфигурации правил и публикация CMDBuild webhooks являются разными
операциями: первая выполняется через `Сохранить в папку` и затем перечитывается
applier'ами, вторая обновляет `etl/webhook` inventory на стороне CMDBuild.

`monitoring-ui-api` пишет файлы атомарно и обновляет `manifest.json` последним.
Runtime services только читают опубликованную конфигурацию.

## Как модель попадает в Zabbix

Меню `Сервисный слой -> Применить в Zabbix` и `Каскадное подавление ->
Применить в Zabbix` выполняют current-card apply только для своего слоя и пишут
команды в отдельный Zabbix topic. Dry-run показывает planned objects, связи,
source membership, наличие `zabbix_main_hostid` и ожидаемые problem tags.

При публикации `zabbixconfig2api` создает или обновляет managed Zabbix Services.
Если несколько source-карточек попали в один target, например несколько
`VPN_HUB` в `ВПН филиалов`, applier хранит membership по target-объекту и
добавляет source-card identity в ключ дедупликации. Поэтому повторная source
карточка не должна затирать предыдущую.

Для source-карточки с `zabbix_main_hostid` создается отдельный source leaf service.
У leaf service выставляются `problem_tags` по
`cmdb2monitoring:source_hostid=<zabbix_main_hostid>`, а на Zabbix host добавляется
такой же managed tag с сохранением уже существующих host tags. После этого
Zabbix Services может сопоставить реальные проблемы хоста с leaf service и
поднять статус вверх по дереву service/suppression.

Если `zabbix_main_hostid` пустой, карточка считается неготовой к Zabbix membership:
dry-run покажет отсутствующую привязку, а publish не создаст source leaf и
удалит прежнее активное membership этой source-карточки, если оно уже было
записано. Карточка остается в статусе ожидания `zabbix_main_hostid` в
membership-диагностике, чтобы оператор видел, что правило совпало, но Zabbix
host еще не готов для source leaf/problem tags.

Webhook может не содержать `zabbix_main_hostid`, даже если значение уже есть в
карточке. Перед сопоставлением правил `cmdbconfigbuilder` догружает из CMDBuild
настроенный readiness-атрибут (`Readiness:ZabbixHostIdAttribute`, обычно
`zabbix_main_hostid`) и добавляет его в source attributes. Поэтому новое
membership может появиться после обычного UPDATE карточки, если карточка
проходит условия правила. Если правило фильтрует по другому обязательному полю
например `Critical`, карточка без этого поля не попадет в группу независимо от
наличия `zabbix_main_hostid`.
Переход от пустого `zabbix_main_hostid` к заполненному входит в semantic
fingerprint, поэтому dedup не должен скрывать штатный второй UPDATE после
создания host в Zabbix.

Эта логика строит service impact model. Она не закрывает и не скрывает зависимые
problem events сама по себе, и отдельный разовый контур подавления активных
событий из cmdb2monitoring не используется. Для production-подавления модель
suppression должна быть развернута в Zabbix как service topology и trigger
dependencies, чтобы подавление работало штатными механизмами Zabbix после
появления или изменения событий.

В `Каскадное подавление -> Применить в Zabbix` после публикации suppression
модели используется блок `Зависимости триггеров`:

1. `Dry-run dependencies` берет сохраненное source membership и связи
   suppression-объектов, затем показывает, какие aggregate triggers и trigger
   dependencies будут построены.
2. Командный target правила считается причиной/родителем, related target в
   relation считается зависимым/дочерним объектом.
3. Связи suppression образуют ориентированный ациклический граф, а не одно
   обязательное дерево. Можно строить несколько независимых цепочек, несколько
   верхних причин, ветвления и схождения в общий downstream-объект. Все цепочки
   не обязаны сходиться к одному элементу; обязательны только правильное
   причинное направление и отсутствие циклов.
4. Для каждого suppression-объекта создается единый managed aggregate trigger
   на техническом host `cmdb2monitoring-suppression-aggregates` и managed
   calculated item. Сервис публикует формулу, а текущее состояние рассчитывает
   Zabbix по выбранным triggers source-host. По умолчанию выбираются triggers с
   тегами `scope=availability` или `component=health`; в формулу попадает их
   раскрытое Zabbix expression. Поэтому ICMP, HTTP, agent-проверки и другие
   проверки используют то же условие, по которому source-host дает Problem.
5. `aggregation_type` управляет выражением trigger над healthy-count calculated
   item: `all` срабатывает, если здоровы не все source-host, `any` - только если
   нет ни одного здорового source-host, `threshold` - если здоровых меньше
   заданного процента, `n_of_m` - если здоровых меньше `n`.
6. Triggers source-хостов дочернего объекта и aggregate trigger самого
   дочернего объекта получают dependencies на aggregate trigger родительского
   объекта. Прямые dependencies на отдельные triggers source-хостов причины не
   создаются.
   В Zabbix это не создает отдельную запись `Show suppressed problems`: пока
   родительский trigger находится в Problem, dependent trigger не переходит в
   Problem и будет переоценен только после восстановления родителя и прихода
   новой метрики.
7. При публикации сохраняются ручные Zabbix dependencies; удаляются только
   устаревшие зависимости, которые ранее были записаны этим сервисом как
   managed.
8. Если у source-карточки нет `zabbix_main_hostid`, нет membership или нет активных
   triggers, dry-run покажет предупреждение и по этому участку зависимость не
   будет создана.

После применения suppression membership из Kafka сервис автоматически запускает
тот же пересчет aggregate triggers и dependencies с небольшой задержкой
`ZabbixTriggerDependencies:AutoReconcileDebounceSeconds`. Отдельную кнопку
`Опубликовать зависимости триггеров` используйте для dry-run, ручного контроля и
повторного применения после изменения связей правил или схемы.

Пример: `ВПН Хабы` обычно имеют `aggregation_type=any`, потому что один живой
VPN-хаб еще сохраняет связность. Downstream-объекты не зависят от triggers
отдельных VPN-хабов. Они зависят от aggregate trigger `ВПН Хабы недоступны как
группа`, который перейдет в PROBLEM только когда все source-host VPN-хабов
находятся в проблеме.

## Снижение повторной реакции на свои webhooks

CMDBuild не передает надежный признак, что webhook был создан нашим же
обновлением карточки или связи. Поэтому входной сервис `cmdbwebhooks2kafka`
сохраняет все события в raw Kafka topic, а подавление повторной работы делается
позже.

Алгоритм:

1. `cmdbconfigbuilder` сопоставляет webhook с правилами.
2. Для каждого matched rule он считает semantic fingerprint по тем полям,
   которые реально влияют на правило: class/card/event kind, условия выборки,
   `${source.*}` placeholders, target idempotency key и managed target values.
3. Если для того же `rule_id + source class + source card` уже был такой же
   fingerprint в окне `SemanticDeduplication:WindowSeconds`, новая команда не
   публикуется.
4. `cmdbaggregation2cmdbuild` перед обновлением managed target-card читает
   текущую карточку. Если значения уже совпадают, он не делает `PUT` в CMDBuild.
5. Создание relation остается идемпотентным: существующая связь считается
   `skipped`.

Практический вывод для редактора правил:

- не добавляйте в managed target-поля значения, которые меняются на каждый
  no-op, например текущий timestamp;
- не меняйте `population_source_key` в обычном процессе редактирования:
  в materialized-шаблонах он должен быть стабильным ключом измерения;
- выбирайте стабильный idempotency key;
- если изменение должно обязательно вызвать пересчет, поле должно участвовать
  в условиях правила или в `${source.*}` mapping;
- повторные raw webhooks после update domain/card могут быть видны в UI, но
  одинаковое смысловое состояние не должно создавать новые aggregation
  commands.

## Диагностика

Если после изменения карточек CMDBuild нет ожидаемых изменений:

1. Убедитесь, что карточка имеет `zabbix_main_hostid`, если это CREATE или UPDATE
   для Zabbix-цепочки.
2. Проверьте managed webhooks онлайн: для каждого source-класса должны быть
   покрыты CREATE, UPDATE и DELETE, либо должен быть global webhook. Если
   webhook явно перечисляет payload-поля, в списке должны быть поля условий,
   измерения population, `${source.*}` mappings и idempotency key.
3. Проверьте, что после сохранения конфигурации и перечитывания applier'ов было
   новое событие source-класса или был выполнен `Запросить применение текущих
   карточек`. Применение шаблонов само по себе не пишет target-карточки
   service/suppression.
4. Проверьте raw Kafka topic в UI `События`.
5. Проверьте health и loaded rule version у `cmdbconfigbuilder`.
6. Проверьте, что source class действительно совпадает с regex правила или
   шаблона.
7. Проверьте, что field identifier в условии выборки есть в событии или может
   быть получен runtime-логикой.
8. Если raw webhook есть, но aggregation command не появился, проверьте
   `SemanticDeduplication`: событие могло быть подавлено как повтор того же
   semantic fingerprint.
9. Временно включите `Debug:Enabled=true`, `Debug:Level=Basic`; для глубокого
   разбора используйте `Verbose` коротким окном.

Если в шаблоне мало атрибутов:

- обновите CMDBuild cache;
- проверьте, какие классы реально выбрал `Source class regex`;
- проверьте, возвращает ли CMDBuild inherited attributes для конкретного
  класса;
- используйте stable латинские attribute codes, а русские названия храните в
  description/help;
- разделите шаблон, если выбранные классы имеют разные наборы полей.
