Как читать результат проверки

Цикл есть только когда по направлению проверки можно выйти из объекта и вернуться в него же. Такой контур нужно разрывать перед отражением модели в Zabbix.

Не цикл - это однонаправленная цепочка или прямое ребро, которое дублирует путь через промежуточный объект. Такая связь может быть лишней или транзитивной, но сама по себе не создает кольца.

  • Подавляет: причина скрывает симптомы цели, например Core -> VPN.
  • Зависит от и Использует: в режиме влияния стрелка идет от зависимости к зависимому объекту.
  • Влияет на: слабая причинная связь для анализа, в Zabbix-графе считается направленной связью влияния.
  • Содержит: сервисная агрегация состава; в подавлении не используется.

    • Сервис города собирает оба блока в один бизнес-узел для сервисного дерева.

    Какой Тип связи использовать для сервисной цепочки:

    • Содержит выбирайте только для сервисных агрегаций, под которые есть домен схемы: Пул рабочих мест города -> Группа рабочих мест, Группа рабочих мест -> Платформенный сервис. Для связи сервиса или пула с сетевой зоной используйте Использует или Зависит от.
    • Использует выбирайте, когда объект сервиса потребляет ресурс, но это не обязательно жесткая причина недоступности: Пул рабочих мест города использует Сетевую зону доступа города, сервис рабочего места использует общий сетевой ресурс.
    • Зависит от выбирайте для жесткой технической зависимости: Сервис города зависит от Маршрутизаторов ядра или Сетевой зоны доступа. Если цель справа недоступна, источник слева должен считаться затронутым.
    • Влияет на выбирайте для слабой причинно-следственной связи, которую нужно видеть в анализе влияния, но не трактовать как жесткую зависимость: перегрузка сетевой зоны влияет на пул рабочих мест, но не всегда означает полную недоступность.

    Пример: рабочее место филиала

    Для цепочки лучше задавать связи от бизнес/потребляющего объекта к технической причине:

    Сервис рабочих мест -> Ноутбуки: тип связи Содержит.

    Сервис рабочих мест -> Маршрутизаторы филиалов: тип связи Зависит от.

    Маршрутизаторы филиалов -> ВПН хаб: тип связи Зависит от.

    ВПН хаб -> Маршрутизаторы ядра: тип связи Зависит от.

    Итоговая логика: Сервис рабочих мест содержит Ноутбуки и зависит от цепочки Маршрутизаторы филиалов -> ВПН хаб -> Маршрутизаторы ядра.

    Если нужен более детальный уровень, можно задать Ноутбуки -> Маршрутизаторы филиалов как Зависит от. Тогда сервис рабочих мест содержит ноутбуки, а доступность ноутбуков объясняется сетевой цепочкой: сервис пострадал не напрямую от маршрутизатора, а через конкретный слой рабочих мест.

    Рабочее место филиал / City14 -> Рабочие места / City14: тип связи Содержит. Филиальный сервис включает парк рабочих мест как составную часть. Это не техническая причина отказа, а иерархия/состав сервиса.

    Рабочие места / City14 -> Маршрутизаторы филиала / City14: тип связи Зависит от. Рабочие места считаются доступными только если доступна локальная сеть/маршрутизаторы филиала.

    Маршрутизаторы филиала / City14 -> ВПН филиалов: тип связи Зависит от. Филиальная сеть зависит от VPN-уровня для связи с центральной инфраструктурой.

    ВПН филиалов -> Маршрутизаторы ядра: тип связи Зависит от. VPN-уровень зависит от ядра/центральной маршрутизации.

    Рабочие места / City14 -> ПО/платформенный сервис, если рабочие места используют приложение, VDI, AD, DNS, DHCP и т.п.: тип связи Использует. Это функциональная зависимость от сервиса, который нужен рабочим местам, но не является физической частью филиала.

    Маршрутизаторы филиала / City14 -> Канал связи или Провайдерский сервис, если такой объект заведен отдельно: тип связи Использует. Маршрутизаторная зона использует внешний транспорт/канал, но канал не содержится внутри маршрутизаторов.

    Рабочее место филиал / City14 -> SLA policy: тип связи Имеет SLA / has_sla_policy. SLA задается на бизнес- или сервисный агрегат, а не на каждый ноутбук.

    Короткое правило выбора: Содержит используем для состава; Зависит от - для причины недоступности; Использует - для внешней функциональной опоры, которая не является составной частью объекта слева.

    Бизнес-цепочка подавления

    Зона подавления филиала -> Сетевая зона доступа -> Хосты или рабочие места филиала.

    • Если падает сетевая зона филиала, события рабочих мест этого филиала должны подавляться.
    • Если падает ядровой маршрутизатор, подавляются нижестоящие зоны и зависимые оконечные объекты.
    • Прямая связь правило-правило нужна для единичной жесткой зависимости, где шаблон не нужен.

    Какой Тип связи использовать для цепочки подавления:

    • Подавляет выбирайте, когда событие источника должно скрывать симптомы цели: Core Router Down подавляет события Сетевой зоны доступа, а Зона подавления филиала подавляет события рабочих мест филиала.
    • Зависит от выбирайте, когда нужно построить цепочку причины без прямого правила подавления: Рабочие места города зависят от Сетевой зоны доступа города, Сетевая зона доступа зависит от Маршрутизатора ядра. Такая связь помогает вывести первопричину.
    • Содержит для подавления недоступен: в стандартной CMDBuild-схеме слоя подавления нет aggregates_to-доменов. Для цепочки причин используйте Зависит от, для фактического подавления симптомов - Подавляет.
    • Влияет на выбирайте для диагностического контекста без автоматического подавления: деградация магистрального канала влияет на филиальные зоны, но решение о подавлении может оставаться ручным или дополнительным.
    • Использует в подавлении применяйте редко: только если нужно зафиксировать потребление общего ресурса без семантики подавления или жесткой зависимости. Для реального подавления чаще нужны Подавляет или Зависит от.

    Регулярные выражения по переменным шаблонов

    Точное сопоставление: шаблон Рабочие места имеет vars.city = ${source.locationFloorBuildingCity}, шаблон Сетевая зона имеет такую же переменную vars.city. В связи выбираются переменная источника city, переменная цели city, оба regexp пустые. Система сравнивает значения целиком. Результат: Рабочие места City04 -> Сетевая зона City04, Рабочие места City15 -> Сетевая зона City15.

    Сопоставление разных форматов двумя regexp: шаблон рабочих мест имеет vars.hostnamePrefix = w04-ntb-001, шаблон сетевой зоны имеет vars.cityName = City04. Regex источника (?i)^w([0-9]{2})-.* дает 04; regex цели (?i)^City([0-9]{2})$ тоже дает 04. Результаты regexp сравниваются: 04 = 04, поэтому связь создается. Для w15-arm-023 и City15 результат 15 = 15. Если один regexp не совпал, например srv-core-01, связь не создается. Если источник дал 77, но целевого результата 77 нет, запись должна попасть в диагностику как несопоставленная.

    Отбор для шаблон-шаблон: у левого и правого шаблона есть отдельные блоки строк. Например слева Включить dimension_key / (?i)^City(04|14)$ допускает к сопоставлению только рабочие места City04 и City14, справа Исключить dimension_key / (?i)^City00$ запрещает целевые сетевые зоны City00. После этого система все равно сравнивает выбранные переменные источника и цели и создает только совпавшие пары.

    Отбор для шаблон-правило: связь направленная, поэтому шаблон может быть как источником, так и назначением. Если шаблон слева, фильтр ограничивает сгенерированные правила шаблона-источника, например dimension_key / (?i)^City(04|14)$. Если шаблон справа, фильтр ограничивает сгенерированные правила целевого шаблона, например правило Core Router подавляет только City04 и City14. Пустой блок означает все сгенерированные правила выбранного шаблона.

    Циклы и транзитивные связи

    Цикл - это замкнутый путь в выбранном направлении проверки: Core -> VPN -> City33 -> Core. Не цикл - это однонаправленная цепочка с дублирующим прямым ребром: Core -> VPN -> City33 и Core -> City33. Такая связь должна попадать в диагностику как транзитивная, но не в список циклов.

    Показать графические примеры циклов
    Цикл или не цикл

    Цикл - это замкнутый путь в выбранном направлении проверки. Не цикл - это цепочка в одну сторону или прямое ребро, которое дублирует путь через промежуточный объект.

    • Подавляет: причина подавляет события цели.
    • Зависит от, Использует, Влияет на: показывают направление влияния после разворота семантики зависимости.
    • Содержит: доступен для сервисного состава и не применяется в подавлении.

    Помощь

    Ключевые правила подготовки CMDBuild и генерации структур Zabbix.

    Порядок работы

    1. Откройте Управление схемами, выберите язык, префикс и корень модели.
    2. Проверьте планируемые и готовые классы/домены отдельно для сервиса и подавления.
    3. Для конкретных классов добавьте связи наполнения с существующими классами CMDBuild заказчика.
    4. Отправьте выбранные классы и домены в CMDBuild кнопкой Отправить выбранное в CMDBuild.
    5. Настройте правила конвертации, подготовьте и сохраните правила по шаблонам и связям, затем откройте Модель -> Применить в Zabbix: в одном блоке выберите слой, режим, SLA и зависимости триггеров.
    6. Подготовить и сохранить правила создает сгенерированные правила и managed_relations, затем сохраняет конфигурацию в папку и обновляет manifest. Целевые карточки сервиса/подавления появляются позже, когда обработчик правил получит подходящие CMDBuild webhooks.

    Корень CMDBuild и суперклассы

    • Корень по умолчанию: /Мониторинг для RU и /Monitoring для EN.
    • Если корень отсутствует, builder создает пустой prototype-суперкласс, например C2M_Monitoring.
    • Сервис и подавление разделяются ниже корня через C2M_ServiceManagedObject и C2M_SuppressionManagedObject.
    • Если старый управляемый суперкласс уже создан под Class, а текущий корень требует другого parent-класса, это конфликт схемы; такой класс нужно удалить или перенести вручную перед применением.

    Сервисная схема

    • Сервисные классы строят дерево сервисов Zabbix.
    • Общие поля находятся в ServiceManagedObject.
    • aggregation_type является lookup: all, any, threshold, n_of_m.
    • В дереве Zabbix Services all означает: service станет Problem только когда все прямые дочерние service уже Problem. any означает: любой дочерний service в Problem поднимает состояние наверх.
    • threshold и n_of_m в сервисном слое сохраняются как политика агрегации и проверяются UI, но текущая публикация дерева Zabbix Services не считает процент или количество без отдельной aggregate-политики.
    • JS-проверки CMDBuild сохраняются в поле validationRules самих атрибутов, а не отдельными объектами схемы.
    • threshold и sla_target задаются процентами от 0 до 100; запятая и точка должны нормализоваться перед отправкой в Zabbix.
    • Связи зависимости между конкретными service-классами строятся через матрицу доменов service_depends_on; member_of и aggregates_to остаются для состава и агрегации.
    • ServiceSlaPolicy хранит авторитетную SLA-политику в CMDBuild и связывается с сервисными объектами через has_sla_policy. Если явной связи нет, применяется fallback из ZabbixSla:DefaultPolicyKey.
    • ServiceSlaCalendar хранит переиспользуемые календари SLA и связывается с политикой через has_sla_calendar. В календаре семь полей дней недели: monday_hours ... sunday_hours, формат значения HH:mm-HH:mm, например 09:00-18:00; пустой день выключен. Если связи has_sla_calendar нет, календарь считается ручным/внешним. Поле ServiceSlaPolicy.calendar остается только как legacy/внешний код.
    • ServiceSlaDowntime хранит регулярные окна исключения SLA и связывается с политикой через has_regular_downtime. Ручные разовые downtime в Zabbix сохраняются, если их имя не начинается с managed-префикса ZabbixSla:ManagedExcludedDowntimePrefix.

    Схема подавления

    • Классы подавления строят зависимости для подавления каскадов Zabbix.
    • Все классы подавления наследуют одинаковые общие атрибуты; исключение: SuppressionProxyGroup.fallback_supported.
    • В подавлении те же значения aggregation_type считаются по contributing source-hosts aggregate trigger-а: all становится Problem, если здоровы не все выбранные source-hosts; any - только когда не осталось ни одного здорового source-host; threshold и n_of_m используют поля threshold и n.
    • Домены подавления имеют одинаковые атрибуты связи: is_active, priority, source.
    • is_dynamic не используется: изменение состава агрегата является штатным пересчетом управляемых связей.

    Управляемые связи и удаление

    • Домены создаются с удалением связи при удалении связанной карточки.
    • Если объект выходит из агрегата, builder-сервис удаляет устаревшую связь при сверке желаемого состояния.
    • Если меняются IP, DNS, hostname, tags или status карточки, это обычное обновление объекта.
    • zabbix_main_hostid является признаком готовности карточки к Zabbix-цепочке; CREATE и UPDATE без него не должны создавать членство в агрегате.
    • В правиле автонаполнения целевой класс означает создание или обеспечение экземпляра; атрибуты зоны ответственности пользователя автоматика не заполняет.
    • В статических правилах атрибуты создаваемого целевого объекта могут использовать только значения выбранного класса: ${class.code}, ${class.description}, ${class.hierarchyPath} и функции над ними. ${source.*} используется только в маппингах времени обработки правил.
    • Агрегатор удаляет заказчик; после DELETE builder-сервис убирает соответствующие структуры из Zabbix.

    Как Zabbix привязывает проблемы к модели

    • Managed service в Zabbix показывает объект сервисной модели, например ВПН филиалов. Сам по себе service tag не говорит Zabbix, какие события хостов входят в этот объект.
    • В сервисном слое для исходной карточки с zabbix_main_hostid applier создает leaf-сервис источника и добавляет его child-узлом к целевому managed service.
    • На source leaf service выставляется problem_tags по cmdb2monitoring:source_hostid=<zabbix_main_hostid>, а такой же tag добавляется на Zabbix host с сохранением уже существующих host tags.
    • После этого реальные проблемы Zabbix host наследуют tag и могут попадать в source leaf, а статус поднимается вверх по дереву сервисов.
    • В подавлении по умолчанию Apply:CreateSuppressionServices=false: leaf-узлы источников, problem tags и отдельное дерево Services не создаются; публикация обновляет только состав для aggregate triggers и зависимостей триггеров.
    • Если zabbix_main_hostid пустой, карточка считается неготовой: dry-run покажет отсутствующую привязку, publish уберет прежнее активное membership этой карточки и оставит ее в pending-диагностике до следующего UPDATE с hostid.
    • Сервисный слой строит модель влияния в Zabbix Services. Реальное штатное каскадное подавление строится публикацией aggregate triggers и trigger dependencies; разовое подавление активных событий в UI не используется.
    • Для сайзинга зависимостей триггеров leaf/source trigger-ы должны подавляться только ближайшей suppression-группой. Причины между группами разворачиваются транзитивно в выражениях aggregate trigger на N уровней, где N задается в конфигурации zabbixconfig2api. UI читает это значение из настроек микросервиса; если администратор изменил N в UI, но еще не нажал Применить настройки UI, ручной dry-run/apply зависимостей использует выбранное значение как одноразовый override, а автоматический reconcile продолжает брать сохраненную настройку микросервиса. При N=2 городская группа видит прямую upstream-группу и следующую причину выше; при N=3 добавляется еще один уровень. Aggregate trigger группы становится PROBLEM, если отказали свои source-hosts по aggregation_type или если upstream-группа в пределах N уже в PROBLEM. Selector состояния группы и selector dependency-покрытия разделены: первый выбирает triggers для формулы calculated item, второй - leaf/source triggers, на которые ставятся dependencies. В деталях dependencies показывается причина состояния: свои source-hosts, upstream или оба варианта, а также unsupported aggregate items с текстом ошибки Zabbix, если формула calculated item не принята.

    Webhooks и правила

    • В меню Администрирование -> Webhooks кнопка Перечитать из CMDBuild загружает текущий список управляемых webhooks, а Сверить правила онлайн сравнивает его с текущими правилами.
    • Кнопка Опубликовать webhooks в CMDBuild создает или обновляет по три управляемых webhook на каждый класс-источник текущих правил: create, update и delete.
    • В меню Управление правилами -> Подготовить и сохранить правила блок Сохраненная конфигурация показывает публикацию правил, шаблонов и связей для микросервисов. После сохранения applier'ы перечитывают эту общую папку, а в целевой схеме аналогично будут читать конфигурацию из Git.
    • Для каждого класса-источника правила должны быть покрыты события CREATE, UPDATE и DELETE. Если webhook описан без classCode, он считается общим для всех классов.
    • Если управляемый webhook явно перечисляет поля payload, онлайн-проверка сверяет их с полями, которые нужны условиям правил, шаблонам цели и ключу идемпотентности. Webhook без списка полей считается передающим полный payload.
    • Чужие webhooks не учитываются: проверяются только записи с настроенным управляемым идентификатором.

    Повторные webhooks

    • CMDBuild не передает надежный признак, что webhook появился из-за записи нашего сервиса. Поэтому raw-топик webhooks сохраняет все события без фильтрации по времени или предполагаемому источнику.
    • cmdbconfigbuilder считает семантический fingerprint для совпавшего правила и карточки-источника. Если поля, влияющие на правило, ключ идемпотентности цели и управляемые значения цели не изменились, повторная команда агрегации не публикуется в пределах окна SemanticDeduplication.
    • cmdbaggregation2cmdbuild перед обновлением управляемой карточки читает текущее состояние и не делает CMDBuild PUT, когда значения уже совпадают.
    • Если raw webhook виден, а новой команды нет, это может быть штатное подавление повторного семантического состояния, а не ошибка доставки.

    Шаблоны автонаполнения

    • Шаблон не исполняется микросервисом напрямую: он материализуется в обычные правила с меткой generated_from_template.
    • Управление правилами -> Подготовить и сохранить правила -> Проверить шаблоны выполняется перед материализацией: проверяет выбранные исходные классы, значения dimension.*, целевые атрибуты, будущие create/update/remove и управляемые связи. Кнопка подготовки правил активна только после проверки без блокирующих ошибок.
    • ID шаблона является стабильным ключом управляемых правил. После первого сохранения он блокируется в редакторе; новый шаблон с уже существующим ID не сохраняется поверх старого.
    • Классы-источники выбираются регулярным выражением по коду, описанию или пути наследования класса.
    • Измерение заполнения задает, по каким значениям шаблон развернется в статические правила. Новая модель генерирует правила по схеме класс-источник x значение измерения: например один шаблон для NTBook|ThinClient|ARM и измерение "город" создают отдельные сгенерированные правила на каждый город.
    • Типы измерения: уникальные значения поля источника, lookup, bool, reference/domain, regex-вырезка, генератор диапазона/списка и статический список. Lookup берется из CMDBuild lookup catalog; reference path вроде ARM -> Building.City читает карточки Building, а не полный набор ARM. Полный source scan остается только для уникальных значений самого source и regex-вырезки.
    • Если source-regexp выбрал несколько классов и у одного класса нет карточек или значений dimension.*, проверка показывает предупреждение и продолжает строить правила по остальным классам. Это становится блокирующей ошибкой только когда шаблон в целом не породил ни одного правила.
    • ${dimension.key} — стабильный технический ключ значения измерения. ${dimension.value} — значение для сравнения, обычно совпадает с key. ${dimension.name} — отображаемое имя после поля Шаблон имени измерения. Для lookup/reference/domain leaf ${dimension.stableValue} хранит code/key/id, а ${dimension.displayValue} хранит description/name/label. ${dimension.regexKey} — безопасная для regexp версия key.
    • Пути reference/domain классифицируются по конечному leaf-атрибуту: lookup leaf показывается в Значения lookup, boolean leaf в Булевы значения, строковый/числовой leaf в уникальных значениях или regex. Если рекурсии не хватило и путь остановился на ссылке на объект, поле попадает в диагностический тип "Неразрешенные reference/domain-ссылки" и такой шаблон нельзя сохранить.
    • Если Регулярное выражение класса-источника выбирает несколько классов, список атрибутов в Условия выборки объектов строится как объединение по всем найденным классам. UI берет активные/читаемые атрибуты каждого класса, разворачивает пути reference и domain до листовых полей и схлопывает дубликаты по идентификатору поля.
    • Одинаковые унаследованные/общие атрибуты показываются один раз. UI не достраивает унаследованные атрибуты обходом цепочки parent-классов: они видны только если API схемы CMDBuild возвращает их для конкретного класса.
    • Фильтры одного шаблона копируются во все сгенерированные правила для всех классов-кандидатов. Выбирайте поля, которые есть у всех классов регулярного выражения, либо разделяйте шаблон на несколько более узких выражений.
    • Поле Атрибуты источника для копирования показывает те же идентификаторы полей источника, которые доступны условиям выборки. Используйте копирование атрибута для JSON/regex-поля или копирование ${source.*} для шаблонов времени обработки.
    • Атрибуты создаваемого целевого объекта в шаблоне или статическом правиле заполняют пользовательские поля агрегата: для сервиса и подавления это is_critical, aggregation_type, threshold, n, если они есть в выбранном целевом классе. is_critical сейчас не влияет на расчет доступности, severity trigger-а, Zabbix service algorithm или suppression aggregate formulas. Это не то же самое, что most critical в Zabbix Services: там выбирается самый тяжелый текущий статус дочерних service. При публикации managed Zabbix service флаг попадает в Zabbix только как service tag cmdb2monitoring:is_critical. Для существующего target-экземпляра Code, name и Description не редактируются, но поля агрегации сохраняются в правиле и используются runtime-командами.
    • Сохранение шаблона фиксирует версию в templateVersions. Применение шаблонов делает сверку по стабильному managed_key и artifact_fingerprint: неизмененные сгенерированные правила не перезаписываются, измененные обновляются, устаревшие правила попадают в templateDeletionPlans.
    • Связи шаблон-шаблон и шаблон-статический класс/карточка должны формироваться по той же схеме: версия нужна для аудита, а операции create/update/delete считаются по managed_key и fingerprint полезной нагрузки.
    • Связи шаблон-шаблон, шаблон-правило и правило-правило создаются в Модель -> Связи. Выберите слой Сервис или Каскадное подавление и тип редактора; сервисный слой показывает только сервисные шаблоны/правила, слой подавления только шаблоны/правила подавления.
    • Связи шаблон-шаблон задаются в два шага: сначала можно отфильтровать сгенерированные правила левого и правого шаблона строками Включить/Исключить, затем выполняется сопоставление переменных двух шаблонов через переменную источника, переменную цели и необязательное регулярное выражение. В шаблон-правило источник и назначение выбираются из шаблонов и правил; UI требует ровно один шаблон и одно правило и показывает направление в списке связей. Связь правило-правило всегда однозначная.
    • population_source_key является служебным ключом управляемой цели. В материализованных шаблонах он формируется из ключа измерения, обычно ${template.id}:${dimension.key}; вручную он не редактируется.
    • name, начальное description и атрибуты создаваемого целевого объекта могут использовать ${template.id}, ${class.code}, ${class.description}, ${dimension.key}, ${dimension.value}, ${dimension.name} и ${vars.name}. ${source.*} для создаваемой цели запрещен, потому что конкретная карточка еще не обрабатывается.
    • Для reference, lookup и domain-атрибутов используйте имена из списка атрибутов класса-источника: ${source.ownerEmail} для reference Owner -> Email, ${source.status} для lookup Status, ${source.domainNetworkSegmentCode} для domain NetworkSegment -> Code, ${source.domainServiceOwnerEmail} для domain Service -> Owner -> Email.
    • Для переменных шаблона и целевых полей доступны функции extract, replace, lower, upper, trim, default.
    • Повторное применение шаблонов делает сверку: создает недостающие сгенерированные правила, обновляет измененные, не трогает совпавшие по fingerprint и переносит устаревшие правила в автоматический план очистки.

    Управление связями

    • Связи описывают бизнес-цепочку между объектами, которые создаются правилами и шаблонами. Они нужны, чтобы сервисное дерево или дерево подавления строилось не плоским списком, а управляемой зависимостью.
    • Сервисный пример: Сервис города -> Сервисная зона сетевого доступа города -> Пул рабочих мест города. Пул рабочих мест объединяет ноутбуки, АРМ и тонкие клиенты по городу; сетевая зона объединяет маршрутизаторы и коммутаторы этого же города; сервис города собирает оба блока в один бизнес-узел.
    • Пример подавления: Зона подавления филиала -> Сетевая зона доступа -> Хосты или рабочие места филиала. Если падает сетевая зона филиала, события рабочих мест этого филиала подавляются; если падает маршрутизатор ядра, подавляются нижестоящие зоны и зависимые оконечные объекты.
    • Шаблон-шаблон используют, когда оба конца связи создаются шаблонами. Например Рабочие места по городам связываются с Сетевая зона по городам по переменной city. Блоки отбора слева и справа только ограничивают, какие сгенерированные правила участвуют; сама пара связи определяется сопоставлением переменных.
    • Шаблон-правило используют, когда один конец создается шаблоном, а второй уже существует как конкретное правило. Направление задается полями Источник и Назначение: шаблон -> правило означает, что сгенерированные правила шаблона будут ссылаться на правило; правило -> шаблон означает, что правило будет ссылаться на совпавшие сгенерированные правила шаблона. Фильтр применяется к той стороне, где выбран шаблон.
    • Правило-правило используют для единичной жесткой зависимости без шаблона: конкретное правило WAN Core зависит от конкретного правила Internet Edge. Такая связь однозначная. Галочка Не показывать связи шаблонов по умолчанию скрывает производные связи правило-правило, которые появились после применения связей шаблон-шаблон или шаблон-правило.
    • Пример "Сервис рабочих мест": связи лучше задавать от бизнес/потребляющего объекта к технической причине. Сервис рабочих мест -> Ноутбуки задавайте как Содержит; Сервис рабочих мест -> Маршрутизаторы филиалов, Маршрутизаторы филиалов -> ВПН хаб, ВПН хаб -> Маршрутизаторы ядра задавайте как Зависит от. Итог: сервис рабочих мест содержит ноутбуки и зависит от цепочки Маршрутизаторы филиалов -> ВПН хаб -> Маршрутизаторы ядра. Если нужен более детальный уровень, задайте Ноутбуки -> Маршрутизаторы филиалов как Зависит от: тогда сервис пострадал не напрямую от маршрутизатора, а через конкретный слой рабочих мест.
    • Пример "Рабочее место филиал": Рабочее место филиал / City14 -> Рабочие места / City14 задавайте как Содержит; Рабочие места / City14 -> Маршрутизаторы филиала / City14, Маршрутизаторы филиала / City14 -> ВПН филиалов, ВПН филиалов -> Маршрутизаторы ядра задавайте как Зависит от; связи к AD, DNS, DHCP, VDI, приложению, каналу связи или провайдерскому сервису задавайте как Использует, если это внешняя функциональная опора, а не состав объекта.
    • Короткое правило выбора: Содержит - состав сервиса; Зависит от - причина недоступности, где отказ цели справа затрагивает источник слева; Использует - внешний сервис или ресурс, который нужен объекту слева, но не входит в его состав.
    • Точное сопоставление переменных: шаблон Рабочие места имеет vars.city = ${source.locationFloorBuildingCity}, шаблон Сетевая зона имеет vars.city. В связи выбираются переменная источника city, переменная цели city, оба regexp пустые. Результат: Рабочие места City04 -> Сетевая зона City04, Рабочие места City15 -> Сетевая зона City15.
    • Regexp для разных форматов: шаблон рабочих мест имеет vars.hostnamePrefix = w04-ntb-001, шаблон сетевой зоны имеет vars.cityName = City04. Regex источника (?i)^w([0-9]{2})-.* дает 04; regex цели (?i)^City([0-9]{2})$ тоже дает 04. Результаты regexp сравниваются, поэтому связь создается: 04 = 04.
    • Если один regexp не совпал, например srv-core-01, связь не создается. Если источник дал 77, но среди целевых сгенерированных правил нет результата 77, запись должна попасть в диагностику как несопоставленная.

    Создать на основе...

    • В редакторах Модель -> Статические правила, Модель -> Шаблоны и Модель -> Связи можно создать новый черновик на основе уже существующего объекта из сервисного слоя или каскадного подавления.
    • Копирование не является живым наследованием: после создания черновика дальнейшие изменения исходного шаблона, правила или связи не меняют новую запись. UI сохраняет только служебный след derived_from, чтобы аудит понимал, откуда взят черновик.
    • Перед созданием черновика блок показывает diff: что будет скопировано, что будет заменено при переходе service/suppression, какие поля не переносятся и что нужно проверить вручную.
    • При копировании между слоями UI пытается сопоставить целевой класс по паре сервисного и suppression-класса, например C2M_ServiceNetworkAccessZone -> C2M_SuppressionNetworkAccessZone. Если целевого класса нет или он не выбирается в текущем слое, поле остается пустым и его нужно выбрать вручную.
    • Связи шаблона или правила не копируются вместе с самим шаблоном/правилом. Для них используйте отдельное Создать на основе... в Модель -> Связи, чтобы явно проверить направление, тип связи и regexp-сопоставление.
    • Создание черновика не сохраняет конфигурацию. Для шаблона нажмите Сохранить шаблон, для статического правила Применить, для связи Добавить связь, затем выполните обычное применение шаблонов/связей и сохранение конфигурации в папку.

    Поля population

    • Заполняйте блок сверху вниз: сначала Регулярное выражение класса-источника и синхронизация CMDBuild, затем Тип развертки. После выбора типа UI оставляет видимыми только поля, которые реально попадут в шаблон.
    • Тип развертки выбирает источник значений измерения: уникальные значения поля источника, lookup, bool, regex-вырезка, диапазон/список, статический список или режим совместимости.
    • Атрибут/путь источника заполняется для уникальных значений поля, lookup, bool и regex-вырезки. Это конечный leaf-атрибут карточки источника или развернутый путь reference/domain. Lookup и bool-поля попадают в свои типы по конечному leaf-типу.
    • ${dimension.key} — стабильный ключ: код lookup, bool true/false, capture-группа, уникальное значение поля или левая часть строки ключ|имя|regex-условия. Его используют в managed/idempotency key.
    • ${dimension.value} — значение для сравнения карточек; обычно оно равно key. ${dimension.name} — имя для текста, которое формирует поле Шаблон имени ${dimension.name}; внутри этого поля ${dimension.name} означает исходное отображаемое имя до шаблона. Для lookup/reference/domain leaf ${dimension.stableValue} означает code/key/id, а ${dimension.displayValue} означает description/name/label. ${dimension.regexKey} — экранированный key для вставки в regexp.
    • Изменение lookup display/name не перемещает membership и не меняет managed key. Подписи обновятся при следующей пересборке affected объекта или после scoped/full reconcile. Использовать display/name как ключ агрегации — плохая практика.
    • В раскрытой подсказке Что такое dimension.* редактор показывает текущий предпросмотр: стратегию чтения, первые рассчитанные dimension.key, dimension.value, dimension.name, dimension.regexKey и итоговый ключ цели. Для reference catalog предпросмотр догружает только конечный класс пути, например Building для ARM.Building.City.
    • Regex вырезки значения и Группа -> ${dimension.key} нужны только для Вырезка regex из поля источника. Пример: regex (?i)^w([0-9]{2})[0-9]{2}-.*$, группа 1. Для именованной группы (?<city>[0-9]{2}) укажите city.
    • Значения измерения / диапазон используется только для Генератор диапазона/списка и Статический список. Диапазон пишется как 00-99; список строками ключ|имя|regex-условия, где ключ станет ${dimension.key}, имя станет базовым именем, а третья часть необязательна.
    • Шаблон ключа цели обычно не меняют: ${template.id}:${dimension.key} дает одну цель на значение измерения. Если нужна отдельная цель на каждый класс-источник, используйте ${template.id}:${class.code}:${dimension.key}.
    • Шаблон имени ${dimension.name} задает отображаемое имя: ${dimension.value}, ${dimension.name}, Город ${dimension.value}. Это не поле карточки источника и не может использовать ${source.*}.
    • Поле отбора карточек-источников появляется для regex/range/static. Для regex-вырезки обычно выбирают то же поле, что и в Атрибут/путь источника; для range/static это обязательное поле, по которому сгенерированные правила будут фильтровать карточки.
    • Regex отбора карточек-источников можно оставить пустым, тогда UI строит точное совпадение со значением измерения. Для шаблонов по hostname можно писать (?i)^w${dimension.regexKey}[0-9]{2}-.*$.
    • Лимит generated-правил находится в Администрирование -> Основные отдельно для сервиса и подавления. Меняйте его осознанно: это защита от случайного создания слишком большого числа сгенерированных правил.
    • population_source_key является служебным ключом управляемой цели и в обычном сценарии пользователем не редактируется. Тип Неразрешенные reference/domain-ссылки диагностический: с ним шаблон сохранить нельзя, нужно выбрать leaf-поле или увеличить глубину рекурсии.

    Регулярные выражения

    • Регулярное выражение класса-источника работает при применении шаблона и выбирает CMDBuild-классы источников. Совпадение проверяется по class.code, отображаемому имени или description и class.hierarchyPath.
    • class означает выбранный класс, а не карточку. Для него доступны ${class.code}, ${class.description}, ${class.hierarchyPath}. Эти значения известны сразу, поэтому их можно использовать в переменных шаблона, extract и replace.
    • source означает конкретную карточку-источник во время обработки события или правила. В Регулярное выражение класса-источника карточки еще нет, поэтому ${source.*} там не используется. В сгенерированном правиле ${source.ownerEmail}, ${source.status}, ${source.domainNetworkSegmentCode} и похожие выражения остаются ссылками времени обработки на поля карточки.
    • Обращение к полям в шаблоне пишется через область и имя: ${class.code}, ${vars.site}, ${source.id}, ${source.ownerEmail}. Имена для source берите из списка атрибутов класса-источника; для reference, lookup и domain UI показывает уже подготовленные идентификаторы.
    • Список полей для условий при нескольких классах-источниках является объединением, а не пересечением. Если выбранное поле отсутствует в части классов, сгенерированные правила для этих классов тоже получат этот фильтр, поэтому лучше сузить regex или использовать общий атрибут.
    • Для выбора нескольких классов по "или" используйте группу и символ |: (?i)^(NTBook|Notebook|ThinClient)$. Такая запись выбирает точное совпадение одного из кодов или имен без учета регистра.
    • Если нужное слово может быть внутри code, description или path, добавляйте .*: (?i).*(Ноутбук|Тонкий клиент|Рабочая станция).*. Для ветки наследования можно писать ^/Monitoring/Infrastructure/.*.
    • Запись (?!)*Тонкий клиент* не означает "содержит Тонкий клиент". В регулярных выражениях * повторяет предыдущий элемент, а не заменяет любую строку. Пишите явно: (?i).*Тонкий клиент.*.
    • Условия выборки объектов работают уже внутри выбранного класса-источника и фильтруют карточки по выбранному атрибуту. Все строки Включить работают как AND; любая строка Исключить удаляет карточку из результата.
    • Примеры фильтров карточек: ^prod-.* для значения с префиксом prod-, .*\\.corp\\.example$ для DNS в домене, ^(10\\.10\\.|10\\.20\\.).* для двух сетевых префиксов, ^$ для пустого значения, .+ для непустого значения.
    • Символы ., +, *, ?, |, (, ), [, ], {, }, ^, $ имеют специальный смысл. Для буквальной точки пишите \\., для плюса \\+.
    • Вырезка подстроки делается не самим регулярным выражением класса-источника, а функцией extract(value, regex, group, fallback). Группа может быть номером или именем: ${extract(class.code, "^C2M_Service(.+)$", 1)}, ${extract(class.description, "^(?<site>[A-Z]{3}) - .*$", "site", "unknown")}.
    • Замена делается через replace(value, regex, replacement, flags): ${replace(class.code, "^C2M_", "")}, ${replace(class.code, "^([A-Z]+)-([0-9]+)$", "$1_$2")}. Для нормализации доступны lower, upper, trim, default.
    • Capture-группы в regexp выборки (...) и (?<site>...) только проверяют совпадение и не становятся переменными автоматически. Чтобы получить значение группы, используйте extract в переменной шаблона или целевом поле.
    • Если нужно развернуть шаблон по фрагменту значения источника, используйте тип измерения Вырезка regex из поля источника. Например поле hostname, capture regex (?i)^w([0-9]{2})[0-9]{2}-.*$, группа 1, а regex условия (?i)^w${dimension.regexKey}[0-9]{2}-.*$.
    • Если набор значений известен без обхода карточек, используйте Генератор диапазона/списка: 00-99, или Статический список строками ключ|имя|regex-условия.
    • Преобразование через extract выполняется при применении шаблона и может читать class.* и уже вычисленные vars.*. ${source.attr} является отложенным значением карточки, поэтому extract(source.attr, ...) сейчас не выполняется при материализации шаблона.

    Безопасное применение

    • Планируемые объекты выбраны по умолчанию, готовые объекты можно выбрать вручную.
    • Применение идемпотентно: существующие классы, lookups и domains пропускаются; атрибуты с измененным validationRules обновляются.
    • Обычные классы отправляются только после корня и суперклассов слоя.
    • Если parent-класс не найден или не создан, зависимый класс/domain не отправляется.

    Redis хранит только runtime-данные: locks, progress, debounce, dedup и cache. Он не является источником истины для правил, membership-state или срезов покрытия. Строка подключения не редактируется в UI и должна задаваться в конфигурации микросервиса или через secret provider.

    Durable state предназначен для membership-state, областей последних изменений и сохраненных snapshot-отчетов. В текущем плане доступны file backend и SQLite backend.
