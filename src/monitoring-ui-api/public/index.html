Помощь

Ключевые правила подготовки CMDBuild и генерации структур Zabbix.

Порядок работы

  1. Откройте Управление схемами, выберите язык, prefix и root модели.
  2. Проверьте planned и ready классы/domains отдельно для service и suppression.
  3. Для конкретных классов добавьте связи наполнения с существующими классами CMDBuild заказчика.
  4. Отправьте выбранные классы и domains в CMDBuild кнопкой Send selected to CMDBuild.
  5. Настройте правила конвертации и выполняйте применение через manual apply.

CMDBuild root и superclasses

  • Root по умолчанию: /Мониторинг для RU и /Monitoring для EN.
  • Если root отсутствует, builder создает пустой prototype superclass, например C2M_Monitoring.
  • Service и suppression разделяются ниже root через C2M_ServiceManagedObject и C2M_SuppressionManagedObject.
  • Если старый managed superclass уже создан под Class, builder переиспользует его, когда root уже существует.

Service schema

  • Service-классы строят дерево сервисов Zabbix.
  • Общие поля находятся в ServiceManagedObject.
  • aggregation_type является lookup: all, any, threshold, n_of_m.
  • JS-проверки CMDBuild сохраняются в поле validationRules самих атрибутов, а не отдельными объектами схемы.
  • threshold и sla_target задаются процентами от 0 до 100; запятая и точка должны нормализоваться перед отправкой в Zabbix.

Suppression schema

  • Suppression-классы строят зависимости для подавления каскадов Zabbix.
  • Все suppression-классы наследуют одинаковые общие атрибуты; исключение: SuppressionProxyGroup.fallback_supported.
  • Suppression domains имеют одинаковые атрибуты связи: is_active, priority, source.
  • is_dynamic не используется: изменение состава агрегата является штатным пересчетом managed-связей.

Managed-связи и удаление

  • Domains создаются с удалением связи при удалении связанной карточки.
  • Если объект выходит из агрегата, builder удаляет stale-связь при сверке desired state.
  • Если меняются IP, DNS, hostname, tags или status карточки, это обычный object UPDATE.
  • В правиле автонаполнения target class означает создание или обеспечение экземпляра; атрибуты зоны ответственности пользователя автоматика не заполняет.
  • Агрегатор удаляет заказчик; после DELETE builder убирает соответствующие структуры из Zabbix.

Шаблоны автонаполнения

  • Шаблон не исполняется микросервисом напрямую: он материализуется в обычные правила с меткой generated_from_template.
  • Source classes выбираются регулярным выражением по коду, описанию или пути наследования класса.
  • name, initial description и population_source_key могут использовать ${class.code}, ${class.description}, ${source.attr} и ${vars.name}.
  • Повторное применение шаблонов удаляет старые generated-правила и создает новый набор, сохраняя ручные правила.

Безопасное применение

  • Planned объекты выбраны по умолчанию, ready объекты можно выбрать вручную.
  • Apply идемпотентен: существующие классы, lookups и domains пропускаются; атрибуты с измененным validationRules обновляются.
  • Обычные классы отправляются только после root и layer superclasses.
  • Если parent-класс не найден или не создан, dependent class/domain не отправляется.
