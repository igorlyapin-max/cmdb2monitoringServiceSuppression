
ТЕХНИЧЕСКОЕ ЗАДАНИЕ
CMDB → ZABBIX CONFIGURATION BUILDER (SUPPRESSION + SERVICE TREE)

Версия: 1.0 (clean)
Назначение: генерация конфигурации Zabbix (dependencies + service tree) из CMDB.
ВАЖНО: система НЕ считает SLA и НЕ обрабатывает runtime-события. Это делает Zabbix.

================================================================================
1. ЦЕЛЬ И ГРАНИЦЫ
================================================================================

Цель:
- устранение каскадных отказов (через trigger dependencies)
- построение корректной сервисной модели для SLA (через Zabbix IT Services)

Границы:
- CMDB — источник истины (объекты, связи, параметры)
- Builder — генерирует конфигурацию Zabbix
- Zabbix — исполняет (триггеры, зависимости, SLA/Service Tree)

Система НЕ:
- не рассчитывает SLA/статусы
- не агрегирует runtime метрики
- не принимает решения о PROBLEM/OK

================================================================================
3. СЛОИ (РАЗДЕЛЕНИЕ СЕМАНТИКИ)
================================================================================

3.1 Suppression Layer (Dependency Graph)
Назначение: подавление каскадов.
Объекты: CI, triggers
Связи: depends_on_*
Выход: trigger dependencies

3.2 Service Layer (SLA Model)
Назначение: описание SLA-логики.
Объекты: Service
Связи: service_depends_on
Выход: Zabbix Service Tree

Ограничение:
- слои независимы, но используют общую CMDB модель
- связи слоёв не смешиваются

================================================================================
4. ЕДИНЫЙ PIPELINE (CONFIG BUILD)
================================================================================

onWebhook(event):
    affected = resolve_affected_ci(event)
    model = build_normalized_model(affected)

    # 1. Suppression config
    deps = build_dependencies(model)
    apply_trigger_dependencies(deps)

    # 2. Service config
    services = build_service_tree(model)
    apply_service_tree(services)

Примечание:
- нет runtime SLA
- нет статусов
- только генерация конфигурации

================================================================================
11. ЧАСТИЧНО ЗАПОЛНЕННАЯ СЕРВИСНАЯ МОДЕЛЬ
================================================================================

11.1. Общий принцип

Система должна корректно работать в условиях неполной (частично заполненной) сервисной модели.

Допускается:

- сервис существует, но не имеет зависимостей
- сервис имеет зависимости, но не имеет ресурсов (CI/Triggers)
- ресурсы существуют, но не привязаны к сервисам
- часть связей задана, часть отсутствует

Система НЕ должна:
- падать
- удалять существующую конфигурацию
- генерировать некорректные зависимости
- блокировать обновление других объектов

--------------------------------------------------------------------------------

11.2. Типы неполных состояний

1. Пустой сервис:

Service:
  exists
  deps = []

Поведение:
- создается Zabbix Service без children
- SLA считается как UNKNOWN или OK (по настройке Zabbix)

--------------------------------------------------------------------------------

2. Сервис без ресурсов:

Service:
  depends_on → Service (или Fleet)
  но нет прямых CI

Поведение:
- создается только иерархия Service → Service
- допустимо

--------------------------------------------------------------------------------

3. Ресурсы без сервисов:

CI:
  существует
  но не участвует в SLA

Поведение:
- участвует только в suppression
- НЕ попадает в Service Tree

--------------------------------------------------------------------------------

4. Частично заданные зависимости:

Service:
  deps:
    - DB
    - (отсутствует API)
    - (отсутствует Auth)

Поведение:
- используются только существующие зависимости
- отсутствующие не считаются ошибкой

--------------------------------------------------------------------------------

11.3. Правила обработки

Builder должен:

1. Быть tolerant к неполной модели
2. Генерировать конфигурацию только из существующих данных
3. Не удалять Service Tree, если часть данных отсутствует
4. Не считать отсутствие dependency ошибкой
5. Логировать предупреждения, но не блокировать pipeline

--------------------------------------------------------------------------------

11.4. Валидация

Ввести уровни проверки:

ERROR (блокирует):
- нет zabbix_hostid для CI, участвующего в dependency
- невозможно разрешить trigger

WARNING (не блокирует):
- сервис без зависимостей
- dependency без ресурса
- aggregation без достаточного числа объектов

INFO:
- частичное покрытие SLA
- неполная модель сервиса

--------------------------------------------------------------------------------

11.5. Поведение apply

Apply должен:

- обновлять только известные части модели
- не удалять существующие children, если данные временно отсутствуют (опционально: режим safe_apply)

Режимы:

safe_apply = true:
  не удаляет отсутствующие связи

safe_apply = false:
  делает полный reconcile

Рекомендуется:
MVP → safe_apply = true

--------------------------------------------------------------------------------

11.6. Пример

CMDB:

Service: Payment
  depends_on:
    - DB
    - (API отсутствует)

Результат:

Zabbix:
PaymentService
  child: DB

→ система работает, SLA считается по DB

--------------------------------------------------------------------------------

11.7. Принцип

Сервисная модель развивается постепенно.

Builder должен поддерживать:
- инкрементальное наполнение
- отсутствие жестких требований к полноте модели
- стабильную работу при частичной конфигурации

--------------------------------------------------------------------------------

11.8. Итог

Неполная модель:
- допустима
- ожидаема
- должна корректно обрабатываться

Полнота модели:
- достигается со временем
- не является prerequisite для работы системы



================================================================================
12. ВЕРСИОНИРОВАНИЕ И ROLLBACK КОНФИГУРАЦИИ ZABBIX
================================================================================

12.1. Назначение

Система должна поддерживать версионирование конфигурации,
чтобы обеспечить:
- откат при ошибках
- аудит изменений
- воспроизводимость состояния

--------------------------------------------------------------------------------

12.2. Объекты версионирования

Версионируются:

1. Trigger Dependencies
2. Zabbix Services (Service Tree)
3. Apply Plan

--------------------------------------------------------------------------------

12.3. Модель версий

table: config_version

- version_id
- timestamp
- source_event_id
- scope (affected CI / services)
- type (full | partial)
- status (applied | rolled_back | failed)

--------------------------------------------------------------------------------

table: config_snapshot

- version_id
- entity_type (dependency | service)
- entity_id
- payload (json)

Пример payload:
- список dependencies для trigger
- структура children для service

--------------------------------------------------------------------------------

12.4. Apply с версионированием

Перед apply:

1. читается текущее состояние Zabbix
2. сохраняется snapshot (pre-state)
3. создается новая версия
4. выполняется apply

После apply:
- версия помечается как applied

--------------------------------------------------------------------------------

12.5. Rollback

Rollback выполняется:

- вручную (оператор)
- автоматически (при ошибке apply)

Псевдокод:

function rollback(version_id):

    snapshot = load_snapshot(version_id)

    for entity in snapshot:
        if entity.type == "dependency":
            restore_trigger_dependencies(entity)

        if entity.type == "service":
            restore_service_tree(entity)

    mark_version_as_rolled_back(version_id)

--------------------------------------------------------------------------------

12.6. Safe Apply и Rollback

При safe_apply = true:

- удаление связей НЕ выполняется
- rollback обычно не требуется

При full reconcile:

- rollback обязателен
- версия должна сохраняться полностью

--------------------------------------------------------------------------------

12.7. Стратегии rollback

1. Full rollback:
   восстановление всей конфигурации

2. Partial rollback:
   только для affected scope

3. Dry-run rollback:
   показать diff без применения

--------------------------------------------------------------------------------

12.8. Валидация перед apply

Перед применением обязательно:

- проверка DAG (для dependencies)
- проверка корректности service tree
- проверка наличия trigger и service в Zabbix

Если ошибка:
- apply не выполняется
- версия помечается как failed

--------------------------------------------------------------------------------

12.9. Аудит

Каждое изменение должно логироваться:

- version_id
- кто инициировал (webhook/manual)
- какие объекты изменены
- diff (before/after)

--------------------------------------------------------------------------------

12.10. Ограничения

1. Zabbix не хранит версии → хранение только на стороне системы
2. Rollback требует полной информации о состоянии
3. Частичный snapshot может привести к неконсистентности → использовать с осторожностью

--------------------------------------------------------------------------------

12.11. Итог

Версионирование обеспечивает:

- безопасное обновление конфигурации
- контроль изменений
- возможность отката

Это обязательный компонент production-системы.


================================================================================
13. КОНФЛИКТЫ И КОНКУРЕНЦИЯ ИЗМЕНЕНИЙ (RACE CONDITIONS)
================================================================================

13.1. Назначение

Система должна корректно обрабатывать параллельные webhook-события и изменения,
чтобы избежать неконсистентной конфигурации в Zabbix.

--------------------------------------------------------------------------------

13.2. Источники конфликтов

- несколько webhook одновременно
- последовательные изменения одного CI
- параллельный apply в Zabbix
- частично устаревший snapshot

--------------------------------------------------------------------------------

13.3. Основные риски

- потеря зависимостей
- перезапись актуального состояния устаревшими данными
- рассинхронизация dependency и service tree
- “дребезг” конфигурации

--------------------------------------------------------------------------------

13.4. Механизмы защиты

1. Глобальная блокировка (lock):

- только один processJob выполняется одновременно
- lock("builder") на время apply

2. Версионирование:

- каждая операция имеет version_id
- apply выполняется только если версия актуальна

3. Очередь событий:

- webhook складываются в очередь
- обрабатываются последовательно

--------------------------------------------------------------------------------

13.5. Идемпотентность

Каждая операция должна быть идемпотентной:

- повторный apply не меняет результат
- одинаковый desired state → одинаковый результат

--------------------------------------------------------------------------------

13.6. Snapshot consistency

Перед apply:

- загружается актуальный snapshot CMDB
- сверяется с source_event_id

Если snapshot устарел:
- задача пересчитывается заново

--------------------------------------------------------------------------------

13.7. Optimistic locking

Каждая версия содержит:

- version_id
- base_version_id

Если base_version устарел:
- apply отклоняется
- выполняется rebuild

--------------------------------------------------------------------------------

13.8. Псевдокод обработки

function processJob(job):

    acquire_lock("builder")

    current_version = get_current_version()

    if job.base_version != current_version:
        release_lock()
        requeue(job)
        return

    desired = build_config(job)

    if not validate(desired):
        release_lock()
        return

    apply(desired)

    new_version = increment_version()

    release_lock()

--------------------------------------------------------------------------------

13.9. Retry стратегия

При конфликте:

- задача возвращается в очередь
- выполняется с актуальным snapshot
- лимит retry (например 3)

--------------------------------------------------------------------------------

13.10. Разделение apply

Apply выполняется в два этапа:

1. Dependencies
2. Service Tree

Если этап 2 падает:
- возможно partial rollback
- система логирует несоответствие

--------------------------------------------------------------------------------

13.11. Консистентность между слоями

Гарантируется:

- dependency и service строятся из одного snapshot
- apply выполняется последовательно

--------------------------------------------------------------------------------

13.12. Аудит конфликтов

Логируются:

- конфликт версий
- retry
- отклоненные apply
- перезапуски задач

--------------------------------------------------------------------------------

13.13. Итог

Система должна:

- обрабатывать события последовательно
- быть идемпотентной
- защищаться от устаревших данных
- гарантировать консистентность конфигурации
