# План развития UI

Документ фиксирует направление упрощения Monitoring UI после стабилизации
графов, шаблонов, dirty scopes и публикации в Zabbix.

Текущее состояние UI полезно как инженерная консоль, но для операционного
использования оно стало слишком громоздким:

- service/suppression имеют параллельные меню с похожей логикой;
- проверки графа выглядят как несколько независимых проверок;
- блоки применения в Zabbix показывают слишком много технического текста;
- синхронизация конфигураций разбросана по нескольким кнопкам;
- сохранение конфигурации и создание generated rules воспринимаются как разные
  операции, хотя в операторском сценарии это один pipeline.

Цель развития: оставить service и suppression разными слоями данных, но
сделать единый операторский сценарий управления моделью, контроля,
синхронизации и публикации.

## 1. Инвентаризация и UX-карта

Текущая навигация уже показывает основные зоны дублирования:

```text
Сервисный слой
  -> Схема
  -> Объекты сервиса
  -> Статические правила
  -> Шаблоны
  -> Управление связями
       -> Шаблон-шаблон
       -> Шаблон-правило
       -> Правило-правило
  -> Применить в Zabbix

Каскадное подавление
  -> Схема
  -> Статические правила
  -> Шаблоны
  -> Управление связями
       -> Шаблон-шаблон
       -> Шаблон-правило
       -> Правило-правило
  -> Применить в Zabbix

Управление правилами
  -> Подготовить и сохранить правила
  -> Визуализация графа связей
  -> Контроль модели

Синхронизация с источниками данных
  -> CMDBuild
  -> Zabbix
  -> Webhooks
  -> Конфигурации конвертации
```

Дублирующиеся или близкие функции:

- шаблоны service/suppression;
- статические правила service/suppression;
- управление связями;
- проверки графа;
- публикация в Zabbix;
- синхронизация конфигураций.

### Карта текущих действий

| Действие | Где сейчас находится | Оценка |
| --- | --- | --- |
| Загрузить/обновить CMDBuild catalog/cache | `Синхронизация -> CMDBuild` и отдельные refresh в рабочих формах | Операторское действие, но должно быть индикатором-светофором с click-to-sync. |
| Загрузить/обновить Zabbix состояние | `Синхронизация -> Zabbix`, `Применить в Zabbix -> Проверить фактическое состояние` | Дублируется; оставить как один статус Zabbix desired/state. |
| Управлять webhooks | `Синхронизация -> Webhooks` | Оставить отдельным техническим экраном, но статус вывести в светофор. |
| Загрузить/сохранить конфигурации конвертации | `Синхронизация -> Конфигурации конвертации` | Разорвано с подготовкой правил; основное сохранение перенести в pipeline подготовки правил. |
| Изменить шаблоны | `Сервисный слой -> Шаблоны`, `Каскадное подавление -> Шаблоны` | Функция одна, отличается слой и слой-специфичные атрибуты. Кандидат на общий компонент с переключателем слоя. |
| Изменить статические правила | `Сервисный слой -> Статические правила`, `Каскадное подавление -> Статические правила` | Функция одна, отличается слой и target classes. Кандидат на общий компонент с переключателем слоя. |
| Изменить связи | шесть экранов: service/suppression x template-template/template-rule/rule-rule | Сильное дублирование; нужен единый редактор связей с типом источника/цели и выбранным слоем. |
| Создать generated rules | `Управление правилами -> Подготовить и сохранить правила` | Pipeline уже выполняет аудит, материализацию и сохранение конфигурации. |
| Проверить шаблоны | внутри `Создать/обновить правила...` кнопка `Проверить шаблоны` | Техническая стадия единого `Контроль модели`. |
| Проверить связи/циклы | `Визуализация графа связей`, `Контроль модели` | Первый summary уже агрегирует граф, циклы и readiness; техническая визуализация остается деталями. |
| Проверить публикацию в Zabbix | `Применить в Zabbix` service/suppression, кнопки dry-run/full dry-run/scope preview | Операторское действие, но должно быть одной кнопкой `Проверить` с scope mode. |
| Опубликовать в Zabbix | `Применить в Zabbix` service/suppression, изменения/full/SLA/dependencies | Операторское действие, но должно быть одной кнопкой `Опубликовать`, где SLA/dependencies являются подэтапами. |
| Посмотреть stale/errors | Zabbix apply blocks, graph control, template audit | Оставить, но свернуть в детали единого контроля/публикации. |

### Что считать самостоятельным действием

Самостоятельные операторские действия:

- синхронизировать конкретный источник по светофору;
- изменить модель;
- подготовить и сохранить правила;
- проверить модель;
- опубликовать в Zabbix;
- удалить stale после явного подтверждения;
- выполнить полный восстановительный прогон.

Технические стадии, которые не должны быть отдельными главными кнопками:

- отдельно сохранить конфигурацию после подготовки generated rules;
- отдельно выполнить `dry-run` как отдельный сценарий вместо кнопки
  `Проверить`;
- отдельно проверять циклы и отдельно проверять готовность к Zabbix как две
  равноправные проверки;
- отдельно публиковать SLA/dependencies как независимые основные сценарии, если
  они являются частью выбранного service/suppression publish pipeline.

### Уточненная целевая структура

```text
Панель
  -> Состояние синхронизации (светофоры)
  -> Здоровье микросервисов
  -> Версии конфигураций
  -> Pending dirty scopes

Модель мониторинга
  -> Слой: service / suppression
  -> Шаблоны
  -> Статические правила
  -> Связи
  -> Объекты сервиса (только service)
  -> Граф и диагностика

Подготовка правил
  -> Контроль модели
  -> Подготовить и сохранить правила
  -> Reload микросервисов

Публикация в Zabbix
  -> Слой: service / suppression / оба
  -> Scope: изменения / полный граф / ручной
  -> Проверить
  -> Опубликовать
  -> Stale cleanup

Администрирование
  -> CMDBuild схема
  -> Webhooks
  -> Настройки микросервисов
  -> SLA настройки
  -> Redis/durable state/coverage
```

### Уточнение для следующих этапов

Первым практическим изменением после инвентаризации должен быть не перенос всех
меню, а добавление компактного блока состояния:

1. Светофоры синхронизации на панели.
2. Summary `Контроль модели` в `Управление правилами`.
3. Новая кнопка `Подготовить и сохранить правила`, которая пока вызывает
   существующие функции.
4. Старые большие блоки остаются как технические детали до стабилизации нового
   сценария.

## 2. Светофоры синхронизации

Синхронизацию надо вынести в компактный блок "Состояние синхронизации".

Индикаторы:

- CMDBuild catalog/cache;
- rules config;
- templates config;
- relations config;
- microservices config version;
- Zabbix desired/state;
- dirty scopes.

Цвета:

- green: актуально;
- yellow: есть локальные/серверные расхождения или требуется действие;
- red: ошибка, недоступность или блокирующее состояние;
- gray: неизвестно или еще не проверялось.

Поведение:

- UI при старте загружает локальный/серверный кэш как рабочее состояние;
- hover показывает источник данных, timestamp, версию, расхождение и
  рекомендуемое действие;
- click выполняет основное действие: синхронизировать, загрузить с диска,
  сохранить, отправить reload микросервисам или перейти к деталям;
- подробные журналы синхронизации остаются в раскрываемых деталях.

Первый реализованный срез:

- на главной панели добавлен блок `Синхронизация`;
- индикаторы показывают CMDBuild, Zabbix, webhooks, правила, шаблоны, связи,
  микросервисы и dirty scopes;
- click по CMDBuild/Zabbix/Webhooks запускает штатные проверки;
- click по правилам/шаблонам/связям сохраняет общую конфигурацию конвертации;
- click по микросервисам обновляет health/version status;
- click по dirty scopes догружает серверный журнал dirty scopes;
- светофор микросервисов показывает расхождения версий правил UI и
  микросервисов, если health endpoint отдает conversion rules status.

Что осталось для следующих срезов этапа 2:

- добавить hover-подсказки с manifest/etag/runtime storage backend;
- вынести подробные журналы синхронизации в раскрываемые детали вместо
  отдельных крупных экранов;
- после появления единого pipeline заменить click по правилам/шаблонам/связям
  на `Подготовить и сохранить правила`.

## 3. Подготовить и сохранить правила

Исходную кнопку:

```text
Создать/обновить правила по шаблонам и связям
```

заменяем операторским pipeline:

```text
Подготовить и сохранить правила
```

или:

```text
Обновить правила и сохранить конфигурацию
```

Pipeline:

1. Выполнить аудит шаблонов и связей.
2. Создать/обновить generated rules.
3. Сохранить service/suppression rules/templates/relations.
4. Обновить manifest.
5. Отметить dirty scopes.
6. Показать итоговые счетчики.

Отдельную кнопку "Сохранить конфигурацию конвертации" нужно убрать из
основного сценария. Ручной экспорт/техническое сохранение можно оставить в
раскрываемом блоке или в администрировании.

Первый реализованный срез:

- меню и основной экран переименованы в `Подготовить и сохранить правила`;
- основная кнопка выполняет аудит шаблонов, материализацию правил/связей,
  отметку dirty scopes и сохранение конфигурации в папку через
  `/api/conversion-config/deploy`;
- результат показывает счетчики service/suppression и версию сохраненной
  конфигурации/manifest;
- отдельный экран `Конфигурации конвертации` пока оставлен как технические
  детали для ручной загрузки/экспорта и диагностики конфликтов.

Что осталось для следующих срезов этапа 3:

- свернуть техническое `Сохранить в папку` в раскрываемый блок;
- добавить явный post-step `Перечитать конфигурацию микросервисов`;
- показывать manifest diff/etag конфликт прямо в pipeline, без перехода в
  технический экран конфигураций.

## 4. Единый контроль модели

Вместо нескольких визуально независимых проверок нужен один блок:

```text
Контроль модели
```

Он агрегирует:

- аудит шаблонов;
- consistency generated rules;
- связи;
- missing targets;
- cycles;
- stale generated rules;
- dirty scopes;
- readiness к Zabbix.

UI показывает один итог:

- `OK`;
- `Warning`;
- `Blocked`.

Детали раскрываются по категориям:

- шаблоны;
- правила;
- связи;
- граф;
- Zabbix readiness.

Backend-функции могут оставаться разными, но для пользователя это одна
проверка модели.

Первый реализованный срез:

- пункт меню `Контроль графов перед Zabbix` переименован в `Контроль модели`;
- сверху добавлен единый summary `OK / Warning / Blocked`;
- кнопка `Проверить модель` запускает аудит шаблонов и пересчитывает общий
  статус;
- summary агрегирует шаблоны, generated rules, связи, циклы, dirty scopes и
  readiness CMDBuild/Zabbix/Webhooks;
- существующая детальная проверка графа Zabbix оставлена ниже как техническая
  детализация.

Что осталось для следующих срезов этапа 4:

- добавить раскрываемые категории вместо всегда видимого списка деталей;
- расширить клики от summary до конкретной строки шаблона/правила/связи,
  когда редакторы получат deep-link на объект.

Второй реализованный срез:

- карточки `Контроль модели` получили действия перехода к месту исправления:
  шаблоны, подготовка правил, связи, граф, настройки и публикация Zabbix;
- в summary добавлена live-готовность публикации Zabbix по последним статусам,
  ошибкам команд, dirty scopes и успешности проверки графа;
- кнопка `Проверить модель` дополнительно обновляет статус публикации service
  и suppression;
- граф связей показан внутри `Контроль модели` как свернутая деталь с итогом
  по обоим слоям; отдельный экран визуализации остается диагностическим.

## 5. Компактная публикация в Zabbix

Нужен один блок:

```text
Публикация в Zabbix
```

Управление:

- слой: `service`, `suppression`, `оба`;
- scope: `изменения`, `полный граф`, `ручной scope`;
- кнопки: `Проверить`, `Опубликовать`.

Dry-run должен быть реализацией кнопки `Проверить`, а не отдельной кнопкой с
другим UX-сценарием.

SLA встраивается как подблок service:

- включена/выключена;
- сколько SLA планируется;
- warnings/errors;
- публикация после service graph.

Suppression dependencies встраиваются как подблок suppression:

- aggregate triggers;
- trigger dependencies;
- warnings/errors;
- публикация после suppression graph.

Большие планы объектов показываются только в деталях с пагинацией и фильтрами.

Первый реализованный срез:

- в экраны service/suppression apply добавлена компактная консоль
  `Публикация в Zabbix`;
- консоль дает единый выбор слоя: `Сервис`, `Каскадное подавление`, `Оба слоя`;
- консоль дает единый выбор scope: `Изменения`, `Полный граф`, `Ручной scope`;
- кнопка `Проверить` вызывает существующий dry-run выбранного слоя/слоев;
- кнопка `Опубликовать` вызывает существующую публикацию и требует успешную
  предварительную проверку выбранных слоев;
- подробные планы, scope, SLA и trigger dependencies оставлены ниже как
  диагностические детали; прямые publish-кнопки позднее удалены.

Что осталось для следующих срезов этапа 5:

Остатка по текущему compact publish срезу нет. Прямые технические кнопки
удалены в этапе 8; основной путь остался через compact-консоль.

Второй реализованный срез:

- compact Zabbix publish сохраняет последний выбор layer/scope/substeps/manual
  scope в локальных UI-настройках;
- добавлен единый progress с отдельными строками service graph, SLA,
  suppression graph и trigger dependencies;
- в progress выводятся счетчики SLA и dependencies, чтобы подэтапы были видны
  без раскрытия технических деталей.

Третий реализованный срез:

- добавлен единый экран `Модель -> Применить в Zabbix` с compact publish
  консолью;
- карточка `Применить в Zabbix` из рабочего пространства модели больше не
  ведет напрямую в service/suppression технические экраны;
- technical service/suppression apply оставлены как раскрываемые детали и
  доступны из единого экрана для диагностики;
- summary единого экрана показывает последние статусы service graph, SLA,
  suppression graph и trigger dependencies.

## 6. Свернуть инженерные простыни

Основные блоки должны показывать краткий summary:

- статус;
- счетчики;
- 3-5 главных ошибок;
- следующее действие.

Подробности должны быть свернуты:

- `Показать детали`;
- `Показать план`;
- `Показать диагностику`;
- `Показать payload`.

Для больших списков нужны:

- пагинация;
- фильтр errors/warnings;
- copy/export.

Help-тексты должны жить в help или раскрываемых справочных блоках, а не
занимать основную рабочую форму.

Первый реализованный срез:

- длинные планы service/suppression публикации в Zabbix свернуты в
  `Показать план и детали ...`;
- план SLA свернут в `Показать план SLA`;
- диагностика trigger dependencies свернута в `Показать диагностику trigger dependencies`;
- диагностика preflight-графа и relation graph свернута в раскрываемые блоки;
- план подготовки правил свернут в `Показать план подготовки правил`;
- основной экран оставляет summary, статус, счетчики и следующую операторскую
  кнопку на виду.

Второй реализованный срез:

- большие справочные блоки preflight, relation graph, service/suppression
  публикации, подготовки правил и административных настроек перенесены в
  раскрывающиеся справочные блоки;
- top errors/top findings добавлены в summary SLA publication, trigger
  dependencies, preflight-графа и visualization graph;
- регрессионные UI-проверки фиксируют наличие свернутых help-блоков и helper-ов
  для главных ошибок.

Что осталось для следующих срезов этапа 6:

- добавить server-side/export JSON для payload/планов, сейчас реализовано
  копирование JSON из UI без отдельного backend-файла;

Третий реализованный срез:

- фильтр `Все / Ошибки / Предупреждения` добавлен в диагностику preflight
  графа, план SLA, trigger dependencies и выводы relation graph;
- добавлено копирование JSON для SLA, trigger dependencies, preflight graph и
  relation graph;
- фильтры работают только на раскрытых технических деталях и не меняют расчет
  модели или публикацию в Zabbix.

## 7. Единый слой вместо параллельных меню

Service и suppression остаются разными слоями данных, но UX должен стремиться к
единому экрану управления моделью:

- переключатель слоя;
- общие компоненты шаблонов;
- общие компоненты статических правил;
- общие компоненты связей;
- слой-специфичные поля внутри формы.

Отдельные пункты меню сохраняются только там, где логика действительно
слой-специфична:

- SLA только для service;
- trigger dependencies только для suppression;
- service objects только для service.

Остальные операции должны постепенно перейти на общие компоненты.

Первый реализованный срез:

- добавлен единый экран `Модель` с переключателем слоя service/suppression;
- на экране показаны общие счетчики: классы, домены, статические правила,
  шаблоны, управляемые связи и pending scope;
- основные действия сведены в общие карточки: схема, статические правила,
  шаблоны, связи, подготовка правил и публикация в Zabbix;
- слой-специфичные действия остаются в том же экране как допустимые карточки:
  `Объекты сервиса` только для service, trigger dependencies остаются внутри
  suppression Zabbix apply;
- старые детальные пункты меню позднее удалены; совместимый путь теперь идет
  через карточки `Модель` и раскрываемые детали единых экранов.

Что осталось для следующих срезов этапа 7:

- остатка по удалению дублирующих service/suppression меню нет.

Второй реализованный срез:

- добавлены единые маршруты `modelRules`, `modelTemplates`, `modelRelations`;
- `Статические правила` и `Шаблоны` открываются через общие экраны с
  переключателем слоя, но используют существующие редакторы и прежний формат
  хранения;
- `Связи` открываются как один редактор с выбором слоя и типа связи
  `шаблон-шаблон`, `шаблон-правило`, `правило-правило`;
- карточки на экране `Модель` переведены на единые маршруты вместо трех
  отдельных relation-карточек;
- добавлены regression-тесты на единые маршруты и selector-ы.

Доработка второго среза:

- help, README и ADMINISTRATION переведены с прямых service/suppression
  маршрутов на `Модель -> Статические правила`, `Модель -> Шаблоны`,
  `Модель -> Связи` и `Модель -> Применить в Zabbix`;
- диагностические сообщения materialization теперь отправляют в единый
  редактор `Модель -> Связи`.

## 8. Миграция без ломки текущего UI

Переход должен быть постепенным:

1. Добавить новые компактные блоки рядом со старыми.
2. Перевести основной сценарий на новые кнопки.
3. Старые блоки пометить как "технические детали".
4. После проверки убрать дублирующие пункты меню.
5. Добавить regression-тесты на новые сценарии.

Регрессионные проверки:

- есть единый "Контроль модели";
- нет дублирующих основных кнопок для одной операции;
- сохранение конфигурации входит в подготовку правил;
- светофоры отображают состояние синхронизации;
- компактный Zabbix apply имеет `Проверить` и `Опубликовать`;
- старые технические детали не мешают основному сценарию.

Первый реализованный срез:

- старые прямые пункты service/suppression сгруппированы в свернутый раздел
  `Технические детали модели`;
- основной вход для операторского сценария теперь `Модель`, где выбирается слой
  и открываются общие операции;
- переходы из карточек `Модель` автоматически раскрывают соответствующий
  технический пункт меню, чтобы пользователь видел, куда попал;
- выбранный слой `Модель` сохраняется в локальных UI-настройках;
- добавлены regression-тесты на техническую группировку, навигацию из модели и
  сохранение выбранного слоя.

Второй реализованный срез:

- `Технические детали модели` скрыты из меню по умолчанию;
- в `Администрирование -> Основные` добавлена настройка
  `Показывать технические детали модели в меню`;
- настройка сохраняется в локальных UI-настройках и включает старые прямые
  service/suppression экраны только для диагностики.

Третий реализованный срез:

- старые технические кнопки Zabbix apply помечены как diagnostic details;
- блоки `Технические детали публикации` скрываются по умолчанию и появляются
  вместе с настройкой `Показывать технические детали модели в меню`;
- основной сценарий публикации остается в compact-консоли `Проверить` /
  `Опубликовать`.

Четвертый реализованный срез:

- старый sidebar-раздел `Технические детали модели` удален физически;
- настройка `Показывать технические детали модели в меню` удалена из
  `Администрирование -> Основные` и из локального payload настроек;
- прямые Zabbix-кнопки `dry-run/publish/full/cancel` и отдельные SLA
  `dry-run/publish` удалены из markup;
- оставшийся путь публикации идет через compact-консоль `Модель -> Применить в
  Zabbix`; подробные планы, scope, stale и diagnostics остаются как детали
  соответствующих экранов.

Что осталось для следующих срезов этапа 8:

- остатка по удалению старых меню и прямых Zabbix-кнопок нет.

## 9. Порядок реализации

Рекомендуемый порядок:

1. Светофоры синхронизации.
2. `Подготовить и сохранить правила`.
3. Единый `Контроль модели`.
4. Компактная `Публикация в Zabbix`.
5. Свернуть старые блоки в технические детали.
6. После стабилизации объединить параллельные service/suppression меню через
   переключатель слоя.

Такой порядок сначала уменьшает шум в ежедневном сценарии и не ломает уже
работающие инженерные функции.
