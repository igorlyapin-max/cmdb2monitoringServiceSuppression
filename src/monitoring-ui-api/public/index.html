Помощь

Ключевые правила подготовки CMDBuild и генерации структур Zabbix.

Порядок работы

  1. Откройте Управление схемами, выберите язык, prefix и root модели.
  2. Проверьте planned и ready классы/domains отдельно для service и suppression.
  3. Для конкретных классов добавьте связи наполнения с существующими классами CMDBuild заказчика.
  4. Отправьте выбранные классы и domains в CMDBuild кнопкой Send selected to CMDBuild.
  5. Настройте правила конвертации и выполняйте применение через Управление правилами -> Верификация и применение.

CMDBuild root и superclasses

  • Root по умолчанию: /Мониторинг для RU и /Monitoring для EN.
  • Если root отсутствует, builder создает пустой prototype superclass, например C2M_Monitoring.
  • Service и suppression разделяются ниже root через C2M_ServiceManagedObject и C2M_SuppressionManagedObject.
  • Если старый managed superclass уже создан под Class, а текущий root требует другого parent, это конфликт схемы; такой класс нужно удалить или перенести вручную перед apply.

Service schema

  • Service-классы строят дерево сервисов Zabbix.
  • Общие поля находятся в ServiceManagedObject.
  • aggregation_type является lookup: all, any, threshold, n_of_m.
  • JS-проверки CMDBuild сохраняются в поле validationRules самих атрибутов, а не отдельными объектами схемы.
  • threshold и sla_target задаются процентами от 0 до 100; запятая и точка должны нормализоваться перед отправкой в Zabbix.

Suppression schema

  • Suppression-классы строят зависимости для подавления каскадов Zabbix.
  • Все suppression-классы наследуют одинаковые общие атрибуты; исключение: SuppressionProxyGroup.fallback_supported.
  • Suppression domains имеют одинаковые атрибуты связи: is_active, priority, source.
  • is_dynamic не используется: изменение состава агрегата является штатным пересчетом managed-связей.

Managed-связи и удаление

  • Domains создаются с удалением связи при удалении связанной карточки.
  • Если объект выходит из агрегата, builder удаляет stale-связь при сверке desired state.
  • Если меняются IP, DNS, hostname, tags или status карточки, это обычный object UPDATE.
  • zabbix_hostid является признаком готовности карточки к Zabbix-цепочке; CREATE и UPDATE без него не должны создавать membership.
  • В правиле автонаполнения target class означает создание или обеспечение экземпляра; атрибуты зоны ответственности пользователя автоматика не заполняет.
  • В модификации автонаполнения атрибуты создаваемого target-объекта могут использовать только значения выбранного класса: ${class.code}, ${class.description}, ${class.hierarchyPath} и функции над ними. ${source.*} используется только в runtime-маппингах правил.
  • Агрегатор удаляет заказчик; после DELETE builder убирает соответствующие структуры из Zabbix.

Webhooks и правила

  • В меню Синхронизация с источниками данных -> Webhooks кнопка Проверить правила онлайн не использует локальный кэш.
  • Проверка онлайн вызывает live endpoint webhooks и сравнивает managed webhooks с source-классами текущих правил конвертации.
  • Для каждого source-класса правила должны быть покрыты события CREATE, UPDATE и DELETE. Если webhook описан без classCode, он считается общим для всех классов.
  • Чужие webhooks не учитываются: проверяются только записи с настроенным managed identifier.

Шаблоны автонаполнения

  • Шаблон не исполняется микросервисом напрямую: он материализуется в обычные правила с меткой generated_from_template.
  • Source classes выбираются регулярным выражением по коду, описанию или пути наследования класса.
  • name, initial description и population_source_key могут использовать ${class.code}, ${class.description}, ${source.attr} и ${vars.name}.
  • Для reference, lookup и domain-атрибутов используйте имена из списка атрибутов source-класса: ${source.ownerEmail} для reference Owner -> Email, ${source.status} для lookup Status, ${source.domainNetworkSegmentCode} для domain NetworkSegment -> Code, ${source.domainServiceOwnerEmail} для domain Service -> Owner -> Email.
  • Для переменных шаблона и target-полей доступны функции extract, replace, lower, upper, trim, default.
  • Повторное применение шаблонов удаляет старые generated-правила и создает новый набор, сохраняя ручные правила.

Regexp в автонаполнении

  • Regexp в Source class regex выбирает классы-источники по code, description и inheritance path.
  • Regexp в Условия выборки объектов выбирает карточки внутри выбранного класса. Все строки Включить работают как AND; любая строка Исключить удаляет объект из результата.
  • (?i).*Workplace.* — выбрать классы, где встречается Workplace без учета регистра.
  • ^Server$ — выбрать только точное имя класса Server.
  • ^(Server|Notebook|PC)$ — выбрать один из перечисленных классов.
  • ^/Monitoring/Infrastructure/.* — выбрать ветку по inheritance path.
  • ^prod-.* — включить карточки, у которых выбранный атрибут начинается с prod-.
  • .*\\.corp\\.example$ — включить DNS-имена в домене corp.example.
  • ^(?!test-).* — включить значения, которые не начинаются с test-; чаще понятнее сделать это отдельной строкой Исключить с ^test-.*.
  • ^(10\\.10\\.|10\\.20\\.).* — включить адреса из двух сетевых префиксов.
  • ^$ — найти пустое значение; .+ — значение должно быть непустым.
  • Символы ., +, *, ?, |, (, ), [, ], {, }, ^, $ имеют специальный смысл. Для буквальной точки пишите \\..
  • Capture-группы в regexp выборки (...) и (?<site>...) используются только для проверки совпадения; они не становятся переменными автоматически.
  • ${extract(class.code, "^C2M_Service(.+)$", 1)} — взять первую группу из имени класса.
  • ${extract(class.description, "^(?<site>[A-Z]{3}) - .*$", "site", "unknown")} — взять именованную группу или вернуть fallback.
  • ${replace(class.code, "^C2M_", "")} — удалить префикс; ${replace(class.code, "^([A-Z]+)-([0-9]+)$", "$1_$2")} — переставить группы.
  • ${lower(trim(vars.site))}, ${upper(vars.code)}, ${default(vars.owner, "monitoring")} — нормализация и значение по умолчанию.
  • Однострочная памятка для разных источников и вырезки: ${class.code} · ${class.description} · ${class.hierarchyPath} · ${vars.site} · ${source.id} · ${source.ownerEmail} · ${source.status} · ${source.domainNetworkSegmentCode} · ${source.domainServiceOwnerEmail} · ${extract(class.code, "^C2M_(.+)$", 1)} · ${extract(class.description, "^(?<site>[A-Z]{3}) - .*$", "site", "unknown")} · ${replace(class.code, "^C2M_", "")} · ${replace(class.code, "^([A-Z]+)-([0-9]+)$", "$1_$2")} · ${lower(trim(vars.site))}.
  • Transform/extract выполняется при применении шаблона и может читать class.* и уже вычисленные vars.*. ${source.attr} остается отложенным значением карточки-источника в обычном правиле; extract(source.attr, ...) требует отдельного runtime-преобразования.

Безопасное применение

  • Planned объекты выбраны по умолчанию, ready объекты можно выбрать вручную.
  • Apply идемпотентен: существующие классы, lookups и domains пропускаются; атрибуты с измененным validationRules обновляются.
  • Обычные классы отправляются только после root и layer superclasses.
  • Если parent-класс не найден или не создан, dependent class/domain не отправляется.
